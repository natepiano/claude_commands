## Model correction

The user caught this: a /clear gives a session a new id, so a session id is not durable across /clear. As planned on 2026-11-01, /clear changes the row id and its children only, so records keyed by the old id go stale. The user's answer: "fixed". The row's id is its first session id and never changes; a separate field holds the current session id, and only /clear or a replaced thread updates it.

## Frame

The user, on item 12: this is basic database design. One fact lives in one place; other records point at it by a fixed id, and a counter identifies its own row.
