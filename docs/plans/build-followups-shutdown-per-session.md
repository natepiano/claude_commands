# Shutdown per session: each session settles, stops and returns on its own

> **Status: IMPLEMENTATION PLAN — phased, delegate-ready.** `/shutdown` keeps one record per session. Each session stops as soon as it is ready and, when a restart was asked for, comes back at once; restarts launch in parallel and are confirmed by the session registry; one session can be taken out, forced or restarted while others are still settling.

## Phases

### Phase 1 — Restarts launch in parallel and are confirmed by the session registry  · status: done

#### As-built

- `_restart_record` runs a real restart in three steps. (1) Every non-seat entry except the requester's is launched through `_launch_entry_safely`: hosts other than `ghostty`, `zed` and `terminal` go to a `ThreadPoolExecutor(max_workers=RESTART_LAUNCH_WORKERS)` with `RESTART_LAUNCH_WORKERS = 6`; those three window hosts launch one after another on the calling thread, because desktop switching needs `WINDOW_DELAY_SECONDS` (1.2 s) between windows. (2) `_confirm_entries` makes one shared wait for every launched id, then calls `confirm_entry` on each. (3) The requester's entry is launched and confirmed alone, last. `_process_seats` and `_finish_record` follow. `_entry_order` keeps only requester-last and name order, so a showrunner launches without any unit live.
- `launch_entry(record: ShutdownRecord, entry: ShutdownSessionEntry, restarted_at: str, desktop_state: DesktopLaunchState, *, dry_run: bool) -> EntryLaunched | EntrySettled` does everything up to and including `_launch_session` and the failed-launch liveness check. `EntryLaunched(relaunching_pending_timers: bool)`: a process was started, or found live after its launcher failed, and the registry must confirm it. `EntrySettled`: nothing is left to confirm (already complete, live and noted, manual, failed, liveness unknown, or any dry run).
- `confirm_entry(record: ShutdownRecord, entry: ShutdownSessionEntry, restarted_at: str, live: bool) -> None`: not live sets `restart failed{session not live after 90 seconds}`; a live showrunner gets its restart note; timers are restored and the entry becomes `restarted` or `timers pending`.
- `wait_for_sessions(session_ids: frozenset[str], timeout: float) -> frozenset[str]` polls `_live_session_ids()` every `SESSION_POLL_SECONDS` (0.5) until every id is live or `timeout` has passed, and returns the ids live at the last poll. `_confirm_entries` passes `SESSION_WAIT_SECONDS` (90.0).
- `_launch_entry_safely` turns any exception from one entry's launch into `restart failed` with the error's reason on that entry and returns `EntrySettled`; the record then ends `restart partial` through `_finish_record`.
- `MachineRestartResult.elapsed_seconds` holds the wall time of `_restart_record`; a real restart ends its result lines with `<machine>: restarted <n> in <s> s` (`_timing_line`). A dry run stays serial, in `_dry_run_entry_order` (units, showrunners, top-level, requester), and prints its former lines.
- `_tmux_launch`: when `tmux new-session` fails and a second `has-session` probe finds the tmux session, it opens a window there; when the session is still absent the original error is raised.
- `add_unit.py`: with a `UnitRestoreLaunch`, `main` records the launch, prints `<unit> restore launched: tmux attach -t <session>` and returns 0 without waiting for remote control (`wait_for_remote_control` is not called), whether it launched the session or found the marked unit already running. New-work launches keep the wait and `--timeout`.
- `sessions.running_session`: a registry record with a non-empty `procStart` is running only when it equals `process_start(pid)`, socket or not; a record without one falls back to the messaging socket.

**Files:**
- `scripts/shutdown/restart.py` — `launch_entry`, `confirm_entry`, `wait_for_sessions`, the three-step `_restart_record`, the timing line, the tmux recovery.
- `scripts/production/add_unit.py` — a restore returns once launched.
- `scripts/message/sessions.py` — `running_session` proves the process whenever a start is recorded.
- `scripts/shutdown/test_restart.py`, `scripts/production/test_add_unit.py`, `scripts/message/test_sessions.py` — the cases for the above; all derive from `ShutdownTestCase`.

**Binds later work:**
- `launch_entry`, `confirm_entry`, `_launch_entry_safely` and `_confirm_entries` take `ShutdownRecord` and `ShutdownSessionEntry` until the per-session shutdown records replace those types; `wait_for_sessions` takes only session ids and does not change with them.
- A dry run prints exactly its former lines in its former order, pinned by `test_restart_dry_run_fixture_preserves_output`. Only a real restart prints the timing line.
- One entry's launch failure never stops the others (`test_one_launcher_exception_leaves_other_entries_restarted`); a relaunch of a single session keeps that rule.
- Record updates from launch threads are serialized by the account lock: `_account_lock` in `scripts/shutdown/record.py`, a `flock` on a new descriptor per call.
- A restore through `add_unit.py` proves nothing about the session; its caller confirms through the registry.

**Gotchas:**
- Slow-restart diagnosis (restart of the claude 3 account, 2026-10-12): eight tmux-hosted sessions took 90 to 92 s each, the whole of `add_unit.py`'s 90 s `--timeout`; ten took 2 to 6 s. `wait_for_remote_control` polls `tmux capture-pane -p` every 0.5 s for `/remote-control is active`, and `capture-pane -p` reads only the visible screen. The panes are 80x24 on the alternate screen with history size 0, and the restart note is 13 to 17 rows tall. On the eight the active line was written 0.26 to 4.64 s before the note, so it was never on the visible screen at a poll; on the ten it was written 0.44 to 2.73 s after the note. Remote control itself was active on all eight within about 3 s: each transcript holds a `bridge_status` entry with the active line, and each registry record's `bridgeSessionId` equals the id in that line's URL. The wait failed on screen layout, not on remote control, so a relaunch is confirmed through the registry and never through pane text.
- `bridgeSessionId` in `~/.claude/sessions/<pid>.json` is the registry field that shows remote control. Its null case was read from the 2.1.296 binary, not observed on a session.
- `sessions.running_session` is stricter than the socket rule and reaches every caller of `running_sessions` and `live_sessions`: a reused pid beside a leftover socket is not running. `inventory.py` already required `procStart == process_start(pid)`, so shutdown's own listing gains no condition. The rule is not yet confirmed on macOS, where `process_start` costs one `ps -o lstart=` call per registry record per call; on Linux it reads `/proc/<pid>/stat`.
- Two entries launched together can share one tmux session that does not exist yet. Creation is not serialized; the launch that loses `new-session` recovers in `_tmux_launch` (`test_parallel_tmux_creation_recovers_by_opening_a_window`). Any rewrite of the launch pool keeps that recovery.

**Ruled out:**
- A lock around tmux session creation: a competing creator can be another process.
- Reading remote control from pane text, or typing into a pane.
- Reporting a session that is back without remote control from `confirm_entry`: no session was in that state.
- A timing line on a dry run: the dry run prints exactly its former lines.

Record-level issues are not carried. An old record that does not validate raises `InvalidRecord` naming the file.

### Phase 3 — Each session stops when ready and returns at once; one conductor per machine  · status: done

#### As-built

- **Store.** `scripts/shutdown/record.py` holds one `SessionShutdown` per session; the account record (`ShutdownRecord`, `ShutdownScope`, `Conductor`), the slot API, `park`/`unpark`/`parked` and `stop_lock` are deleted. `SessionShutdown` and `AccountHold` carry a required `request_id: str`, made once by `down` and given to the peer, so requester-last and hold clearing never compare `requested_at`. `SessionProgress` has `stopping{at}` and `restarting{at, prior}`; `launch-blocked` treats `stopping` as held by name.
- **`migrate(login) -> list[str]`** runs under the account lock, called by `begin`, `conduct`, `up`, `cancel` and `now`. It writes each old-format entry as a session record with `request_id` `legacy-<machine>-<requested_at>`, at most one per session id (a new-format file, else the slot record's entry, else the newest parked record's entry); writes a hold that `account_hold` infers from the old files as `hold.json` without replacing an explicit one; moves `record.json` and `partial/*.json` to `history/`; and returns one line per file, `shutdown: converted the <state> record of <label> from <time>`. An old `cancelled` or `up` record moves to `history/` and writes no session record; record-level issues are not carried. An old file that does not validate, or a conflicting session id, raises `InvalidRecord` naming it before any write or move. Until a writing verb migrates them, `session_records`, `find_session`, `account_hold` and `all_account_holds` read old files through the same private converter, so `status`, `records`, `launch-blocked`, `held-sessions` and a dry run see an old shutdown without changing a file; the old wire types and validators stay private to that converter and no writer uses them.
- **Request.** `settle.begin(login, requested_by, only, *, then, alerts, request_id) -> list[SessionShutdown]` migrates, then creates a `waiting` record, with its Codex seats, for each non-seat session under `only` that has none, and records and stops its timers (a timer stop failure takes that one session out again and names it). A session that has a record is left alone and listed as `already in progress`; with no `only` it sets `hold: "account"` and calls `set_account_hold`. A seat whose owner is not in the request gets no record, and `status` lists it from inventory. `settle.down(account, here, only, *, then, alerts)` keeps the `github-warm-status` check, runs `begin` and starts this machine's conductor, also when every named session already has a record (this resumes a shutdown whose conductor died); unless `--here`, it runs `down <login> --here --requested-by <id> --request-id <request id> [--only …] [--restart] [--no-alert]` on the peer. A peer that is unreachable or refuses prints `<machine>: not reached; run /shutdown there` and never undoes or delays the local shutdown; exit 0 when this machine started.
- **Conductor.** `settle.conduct(login)` holds `record.conductor_lock` without blocking (a second conductor exits 0) and looks again after letting go of the lock, so a request added as it ends is still worked. `StopSession` and the launch half of `RelaunchSession` run in a `ThreadPoolExecutor(max_workers=RESTART_LAUNCH_WORKERS)`, one future per record, and registry waits (`wait_for_sessions`, then `confirm_entry` per id) run in its polling pool; a launch worker never waits for the registry and a record with a running future is skipped, so a 20 s stop wait or a registry entry that never appears delays no other session. Window hosts launch one at a time through the shared desktop state, never through a pool. The conductor ends when no record on this machine has a step left: each is archived, or `stopped` with `then == "stop"`, or needs the user (`stop failed`, `restart failed`, `manual restart`, `timers pending`). It calls `clear_account_hold` when the last record carrying the hold's `request_id` is archived, and on ending sends the requester one result (`report_stop`'s text, key `shutdown-result-<login>`) built from this machine's records plus one read of the peer's `records --json --here`. Every `SETTLE_INTERVAL_SECONDS` it takes one inventory and calls `next_step(record, owner: FreshSession, others: list[SessionShutdown], now) -> Step` for each record, where `Step` is `SendSettleMessage | StopSession | RelaunchSession | Hold(reason: str) | Finished`:
  - `waiting`, settle message due, not the requester → `SendSettleMessage` (a showrunner is messaged at once). The requester's record gets `Hold("requester goes last")` until every other record of the same `request_id` on this machine is finished, failed or archived.
  - `ready` with no blocker and the session and each of its seats idle, or `force == "now"` → `StopSession`. `session absent` or `session identity lost` → `StopSession` too: the stop records `already gone` or `process identity lost`, signals nothing and cleans up. `session account unreadable` → `Hold("account unreadable")`.
  - `stopped`, `already gone` or `process identity lost` → `RelaunchSession` when `then == "restart"`, and `Finished` with the record kept for restore when `then == "stop"`. `restarted` → `Finished`: archived, never launched again.
  - Anything else → `Hold(reason)`. `hold_reason(record, session) -> str` is the one function `status` and the alert both print: `busy`, `showing a form`, `ahead N on <branch>`, `merge in progress`, `Codex seat <name> is still running`, `message queued: <reason>`.
- **Stop.** `stop_session(record: SessionShutdown, *, kill, is_alive, session_record_exists, fresh_inventory, clock, codex_mesh, tmux, sleep) -> SessionShutdown` in `scripts/shutdown/stop.py` claims the record before any signal (`stopping{at}`, under the account lock) and holds a `stop.StopClaim`, checked before every write, signal and cleanup step; a worker whose claim is lost (`StopClaimLost`) yields to its replacement with no user-visible outcome. It runs the identity check, readiness unless forced, `SIGTERM` twice with `STOP_WAIT` and the owner's resource cleanup, and ends `stopped`, `already gone`, `process identity lost` or `stop failed`; a retry on a `stop failed` or already stopped record runs `_retry_owner_cleanup`. `record.stop_incomplete` names a partial stop: `stop failed`, or stopped with cleanup left over (a Codex server or a tmux session still running); `report_stop` alerts the user on one. The conductor and `stop_session` build `FreshSession` (`matching session` with `seats: list[Session]`, `session absent`, `session identity lost`, `session account unreadable`) with the one `_fresh_session`, which never writes an observed pid over the record's.
- **Relaunch.** `relaunch_session(record, *, dry_run, desktop_state)` in `scripts/shutdown/restart.py` claims `restarting{at, prior}` before it launches, also for a `timers pending` record (`launch-blocked --restart-of` exits 1 for `restarting` and not for `timers pending`); `prior` is the progress the claim replaces, and `launch_entry` reads it for the timers-only retry and the unreadable-registry outcome. A confirmed `restarted` record goes to `archive_session`. A stop or relaunch claim younger than `record.CLAIM_STALE_SECONDS` is left to its worker; an older stop claim is retried and an older relaunch claim goes back to `prior`. `up(login, dry_run)` takes each record on this machine that is `stopped`, `already gone`, `process identity lost`, `manual restart`, `restart failed`, `timers pending` or a stale `restarting`: window hosts in order, the rest through the pool, the requester last. A `manual restart` record whose session is live is reconciled (timers restored, archived, no launch), and a real `up` clears the account hold when its last record finishes, also for an account with a hold and no record. `restart(account, …)` runs `up` here and on the peer and decides its alert from both machines' incomplete records, or from every local record when the peer is not reached. A dry run (`up --dry-run`, `restart --dry-run`) calls none of `migrate`, `update_session`, `archive_session` and `clear_account_hold`, prints what it would launch and no `converted` line, and leaves every file where and as it found it.
- **Verbs.** `ready --where` finds the session's own record with `find_session` and sets `where` and `ready` when the progress is `waiting` or `ready`. `cancel` and `now` run on this machine, then on the peer with `--here`. `cancel` withdraws each `waiting` or `ready` record through `record.withdraw_session(login, session_id, restore_and_notify)` (timers and footers back, queued shutdown messages retired, the "cancelled by the user: continue where you were" message sent, the record archived), always clears the account hold, and for each record it keeps (`SessionRetained`) prints `<name> was not cancelled: <progress>; /shutdown restart brings it back` and exits 1. `now` sets `force: "now"` and starts the conductor, which owns every stop and every retry, the retry of a partial stop included. `status` prints what holds each `waiting` or `ready` session (`settle.status_record_lines`, `shutdown._observed_owner`). `alert_user(summary, text, action, *, machine="")` has no scope argument; callers skip the call when the record's `alerts` is `"none"`. `scripts/shutdown/shutdown.py` has no `begin`, `refresh`, `retry-stop`, `stop`, `claim-stop`, `close-failed-stop` or `slot-records` verb; `down` takes hidden `--requested-by`, `--request-id` and `--no-alert`, and `conduct <login>` only calls `settle.conduct`.

- `scripts/shutdown/settle.py` — `begin`, `down`, `next_step`, `hold_reason`, `ready`, `cancel`, `now`, `conduct`, `report_stop`, `alert_user`, `status_record_lines`.

**Binds later work:** The conductor owns every stop and every retry, so the per-session `now` form sets `force` and starts the conductor; it cannot call `stop_session` and print the result. The per-session `cancel` form prints the same kept-record sentence with exit 1, and `record.withdraw_session` withdraws only `waiting` and `ready` records, so withdrawing a failed stop is new work in `record.py`. `status` already prints the hold details; the action lines and the no-conductor line (a probe of `record.conductor_lock`) are unbuilt. Requester-last compares `request_id` among this machine's records, and `up` takes only the progresses listed above. A Remote Control wait in the conductor runs in its polling pool, never on its own thread; the not-answering alert is unbuilt. The skill text and the as-built doc explain each user-visible outcome: a partial stop and its `/shutdown now` retry, the kept-record line and its exit 1, `migrate` refusing conflicting session ids (a diagnostic on stderr, nothing moved), and `restart`'s alert when the peer is not reached.

The readiness types (`ReadinessClear`, `ReadinessBlocked`, `ReadinessCheck`) live in `record.py` because `stop.py` and `settle.py` import each other. `requested_at` has one-second precision; nothing orders or matches records by it, `request_id` does that.

### Phase 4 — Acting on one session: take out, force, restart; what holds each one  · status: done

#### As-built

- `--only NAME[,NAME...]` is public on `down`, `cancel`, `now` and `restart`, and `restart --here` is public. Each item is a session id or an exact session name, resolved against the account's records and inventory on both machines by `shutdown.resolve_sessions(login, items) -> list[str]`; an item matching nothing or more than one session exits 2 with the candidates listed. Resolution never holds local work back for the peer: `--here` resolves on this machine only; a session seen in both records and inventory counts once; an id found on this machine resolves without the peer; when the peer is not reached a name resolves from this machine alone, stderr says `<peer>: not reached; names checked on <machine> only`, and an item found nowhere exits 2 naming the peer as not reached. Every `--only` verb answers `<name>: no shutdown in progress` (exit 1) for a live local session with no record, with no peer call. Without `--only` each verb keeps its account-wide form. Store lookups at the selection and hold-decision boundaries return named outcomes (`record.ShutdownFound` or `record.NoShutdown`; `record.AccountHeld` or `record.AccountOpen`), never a bare optional.
- `cancel --only X` takes out a `waiting` or `ready` record (timers and footers back, queued shutdown messages retired, the session told to carry on, the record archived) and prints `<name>: taken out`. A `stop failed` record whose session is still live gets the same take-out after the stop's identity check and prints `<name>: taken out, still running`; the check and the withdrawal run under the account lock, and a stop claim that wins first keeps the record. A record it cannot take out (`SessionRetained`: `stopping`, `stopped` and every later progress) prints `<name> was not cancelled: <progress>; /shutdown restart --only <name> brings it back` and exits 1; the account-wide form keeps `/shutdown restart brings it back`. The account hold goes through `record.clear_finished_account_hold(login, *, request_ids=())`: it stays while other records of that request remain, and it stays when it belongs to another request.
- `now --only X` sets `force: "now"` on that record alone, calls `_launch_conductor` and prints `<name>: stopping now`; an in-progress record, or a cleanly stopped one with no work left, prints `<name> is <progress>; nothing to stop` and exits 1. `now` stops nothing itself: the conductor owns every stop and every retry, so a `stop failed` record, or a stopped one with leftover cleanup (`record.stop_incomplete`), is retried by the conductor and its result reaches the requester through `report_stop`.
- `restart --only X` runs `relaunch_session` for that record on its machine (through the peer's `up <login> --only <id>` when it lives there), whatever any other record is doing, and skips the requester-last rule, so a stopped requester comes back while its siblings still wait; `--dry-run` and `--no-alert` apply. A `waiting`, `ready` or `stopping` record is refused with `<name> is <progress>, not stopped; nothing to restart` (exit 1, no count, no alert); a record whose `restarting` claim is fresh prints `<name> is already restarting` (exit 0, no launch, no alert). `up` exits `restart.REFUSED_ONLY_EXIT = 4` when a chosen session was refused and nothing failed; `MachineRestartResult` carries `refused: bool` and `local_session_ids`. The account comes from `restart.select_account`.
- `down --only X [--restart]` while another request is in progress adds a record for X only and prints `<name>: added`; repeated for a record with no conductor, it starts conducting and leaves that record's `then`, `hold`, `alerts`, `request_id` and `requested_by` as they were.
- `status` leaves the per-record line of `settle.status_record_lines` unchanged and ends each machine's block with at most one line `no conductor running; /shutdown --only <name> resumes one, /shutdown cancel --only <name> takes it out` (or `conductor ownership unavailable: <reason>`), for `waiting` or `ready` records whose machine has no running conductor, and up to three grouped action lines, `take out: /shutdown cancel --only <name> · <names>`, `stop now: /shutdown now --only <name> · <names>` and `bring back: /shutdown restart --only <name> · <names>`, where `<name>` is printed as those six characters and `<names>` lists the sessions the action applies to. Conductor ownership is a read-only, non-blocking lock probe on the record's machine, locally and through the peer response, answered as running, not running or unavailable: an existing lock file alone proves nothing, and unreadable or unreachable ownership is reported as unavailable, never as no conductor.

**Files:**
- `scripts/shutdown/shutdown.py` — `resolve_sessions`, the `--only` flags, status action lines, dispatch.
- `scripts/shutdown/settle.py` — `cancel` and `now` for chosen records, the no-record lookup `_unrecorded_local_sessions`.
- `scripts/shutdown/restart.py` — `_up` with a selection, refusals, alert scope, `select_account`.
- `scripts/shutdown/record.py` — the failed-stop withdrawal, hold clearing by request, the conductor lock retry, conductor status.
- `scripts/shutdown/test_shutdown_cli.py`, `scripts/shutdown/test_shutdown_status.py`, `scripts/shutdown/test_settle.py`, `scripts/shutdown/test_restart.py`, `scripts/shutdown/test_record.py` — each verb with `--only` by id and by name, and every line above.

**Binds later work:** a refused restart is signalled three ways today (the exit status `restart.REFUSED_ONLY_EXIT`, the bool `MachineRestartResult.refused`, and the unproduced status `"refused"` with `refusal_line`), and the JSON result for `up` replaces all three with one named list, `RestartRefusal`; the lookup for a named session with no record is written twice (`settle._unrecorded_local_sessions`, and inline in `restart._up`) and becomes one function; `restart.select_account` is public; the Remote Control alert follows `_restart_alerts_enabled(login, only, *, here)`, decided from the chosen records only and never for the peer with `--here`; hold clearing is `record.clear_finished_account_hold(login, *, request_ids=())`; the conductor start retry is `record.CONDUCTOR_LOCK_RETRY_DELAYS`; the skill text and the as-built doc describe the printed lines above and the grouped status layout.

**Gotchas:** the status probe holds the conductor lock exclusively for a moment, so `record.conductor_lock` retries for a quarter second (`record.CONDUCTOR_LOCK_RETRY_DELAYS`); without the retry a starting conductor answers "already running" (`ConductorAlreadyRunning`) to a probe. A refused restart is not a failed relaunch: counted as one, it can send the phone alert (`test_selected_restart_refusal_has_no_alert_count_or_summary`). A selected cancel that clears the hold without its request ids can clear a hold another request owns; the kept hold is observable through `launch-blocked` (`test_selected_cancel_of_another_request_keeps_local_account_hold`). `argparse.SUPPRESS` on a subparser prints `==SUPPRESS==`, so `--only` is shown through the hand-written `metavar` help.

**Ruled out:** per-session action and no-conductor lines in `status` (one line per action per machine, naming its sessions, instead).

### Phase 5 — The not-answering alert, the live check, the skill text and the as-built  · status: done

#### As-built

- **Not-answering alert.** On each inventory pass the conductor takes every record that is `waiting`, or `ready` with a `Hold` step, `NOT_ANSWERING_AFTER = timedelta(minutes=5)` after `settle_message.at` when that message was sent and otherwise after `requested_at`, with `alerts: "user"` and no `alerted_at` inside `REPEAT_HOLDOUT_ALERT = timedelta(minutes=60)` (`settle._holdout_due`); `_reserve_holdout_alert` writes `alerted_at` before the send. The records due in one pass share one `settle.alert_user` call (`_send_holdout_alert`): summary `<name> is not answering the shutdown of <label>`, joined by `; `; one text line each, `<machine> <name>: <hold_reason>; /shutdown cancel --only <name> (take it out; it carries on), /shutdown now --only <name> (stop it anyway)`; `ActionRequired` names the same two actions. The requester session gets the same summary and text as a `shutdown` message, key `shutdown-holdout-<login>`. From the Mac the phone send routes `--machine natedev`. Selected shutdowns and requester records alert too, and the alert changes no step.
- **Sends run in a pool.** `_conduct_owned` has a third pool, `notifications`, for the settle message, the not-answering alert and the conductor's Remote Control alert; the sender's timeout is 60 s, and a paused send delays no other session. `_send_settle_message` sends only while the store holds that session's record with the same `request_id` in `waiting`, and saves the delivery under the same condition, so the instruction of a cancelled or replaced request is dropped. An account hold and a session record in any progress leave the UPS alert send untouched (`test_ups_alert_ignores_account_hold_and_every_session_progress`).
- **Remote Control check.** `sessions.remote_control(record: SessionRecord) -> Literal["active", "absent"]` reads `sessions_dir() / "<pid>.json"`: a non-empty string `bridgeSessionId` is `active`; a missing key, an empty value or an unreadable file is `absent`. `restart.wait_for_confirmation(session_ids: frozenset[str], timeout: float) -> RegistryConfirmation` replaces `wait_for_sessions`, which is removed; `RegistryConfirmation(records: tuple[SessionRecord, ...])` keeps the registry records of the final liveness poll and gives `live_ids`. `wait_for_remote_control(records: Sequence[SessionRecord], timeout: float) -> frozenset[str]` polls only `remote_control` for those records every `SESSION_POLL_SECONDS`, never `sessions.live_sessions()`, returns at once when all are active and starts no poll after the deadline. `remote_control_missing(records: list[SessionShutdown], confirmation: RegistryConfirmation) -> tuple[NoRemoteControl, ...]` makes the one wait of a pass (`REMOTE_CONTROL_WAIT_SECONDS = 10.0`) and prints `<name>: running, no Remote Control` for each confirmed session still absent; `record.NoRemoteControl{session_id, name, alerts}` keeps the alert policy after the record is archived. That record still finishes `restarted`; no exit status changes, nothing is relaunched and nothing is typed into a pane. Both confirm stages call it after `confirm_entry`: `restart._confirm_entries` (`up`, here and on the peer) and `settle._confirm_relaunch_pass(records) -> ConfirmedRelaunchPass` in the conductor's registry pool, where an error confirming one record marks that record alone `restart failed`. Cost: a pass that relaunches anything waits usually 1 to 3 s after the registry confirms it, and at most 10 s plus one poll's reads when a session never gets the field.
- **Restart answer.** The internal form `up <login> --here --json` prints one object, `restart.PeerRestartResult{machine, label, outcome: "done" | "partial" | "nothing", lines, no_remote_control: list[NoRemoteControl], refused: list[RestartRefusal]}` (`up_result`; `lines` is what `up` would have printed), and exits 1 when `outcome` is `partial` or `refused` is non-empty. `restart` validates the peer's answer with `parse_peer_result` and prints its `lines`; an exit status other than 0 or 1, or an answer that does not validate, reads as not reached, so both machines run the same version. `RestartRefusal = RestartNotStopped{kind: "not stopped", session_id, name, progress} | RestartNoShutdown{kind: "no shutdown", session_id, name}`, printed through `refusal_line(refusal)`; `MachineRestartResult.refused: list[RestartRefusal]` and `no_remote_control: list[NoRemoteControl]` hold this machine's. `REFUSED_ONLY_EXIT`, the bool `refused`, the status `"refused"` and the `refusal_line` field are removed. `restart` exits 1 on any refusal and sends no alert for refusals alone. `settle.unrecorded_local_sessions(login, ids, records) -> dict[str, str]` is the one lookup for a named session with no record, called by `settle.cancel`, `settle.now` and `restart._up`.
- **Restart alert.** `restart` sends `<label> is not fully back` when something is left to bring back (a local or peer `partial`, or the peer not reached) and `_restart_alerts_enabled(login, only, *, peer: PeerRestartAvailability)` allows it, and also when a session with `alerts: "user"` runs without Remote Control, even as the alert's only lines. `PeerRestartAvailability` is `NOT_ASKED` (`--here`, or every chosen id is local), `NOT_REACHED` (policy from the local records, no second peer call) or `REACHED_TO_BE_READ` (both machines' records). Remote Control lines close with `Turn on Remote Control in each named session at its terminal: /remote-control`, in the text and in `ActionRequired`; the `run /shutdown restart again` sentence appears only when something is left to bring back. The conductor sends the same alert with only the Remote Control lines (`_remote_control_alert`). `--no-alert` and `alerts: "none"` skip the send; the lines still print.
- **Live check.** Not run on either machine. It runs after this code is installed on each machine, on two throwaway sessions picked with `--only`, with `--here` on every `down`, `status`, `cancel` and `restart` and `--no-alert` on every `down` and `restart` (the two verbs that take it). The unit director runs it on natedev and the user on the Mac; both Results lines in the as-built open with `not yet run (2026-10-12)`. The Mac run also confirms `sessions.running_session` there: with one Claude session live, `python3 scripts/message/sessions.py id <its name>` prints its session id.
