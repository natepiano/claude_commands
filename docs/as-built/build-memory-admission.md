# Build memory admission: builds that fit in memory

## What it is

Every build on natedev, CI's and the sessions', is admitted so that it fits in memory, and earlyoom is a last resort rather than a routine event (target: a normal working day with no earlyoom kill). Before this, two admission systems could not see each other: CI ran outside steve in a slice whose limit counted page cache, sessions took steve slots that were admitted before their compilers grew, swap sat full of idle processes so earlyoom's swap condition always held, and a build hold released every session at the same instant. On 2026-10-04, 58 earlyoom SIGTERMs failed whole build steps and CI jobs. Now session builds and their compiles run in one bounded user slice, CI runs in its own smaller slice and slot pool with a kill order below the sessions', build steps sit above both so earlyoom kills the largest build first, every compiling step and every BRP launch waits for free memory before it starts, a build hold releases every held session at once into those gates, and the build log measures all of it: per-slice samples and snapshots, a window memory report, the day's waits, memory kills and CI freshness. The same body of work also hardened neighbors that share these files: the example-test guard in `verify.sh`, prompt reclaim of a cargo token whose `verify.sh` was killed, CI queue-time accounting, BRP launch recording, the disk-floor alerts, the Codex launcher's capacity handling, the dailies Agents section, and broadcasts to every live session.

## How it works

### Machine side (`/etc/nixos`, natedev only)

Not in this repo; listed because the code here reads it.

| Piece | Setting |
| --- | --- |
| `builds.slice` (user slice, `modules/linux/development.nix`) | `MemoryMax=44G`, no `MemoryHigh`, `MemorySwapMax=4G`, `CPUWeight=20` against `app.slice`'s 100, so the sessions and their panes get the CPU first. CI's `hana.slice` sits at 5 against `user.slice`'s 100 (`modules/linux/hana-runners.nix`). Holds every recorded step's scope (`run-*.scope`), the `sccache.service` user service, and the `buildlog` unit (nightly Rust trial, `OOMScoreAdjust=200`). |
| `sccache.service` | Runs the server in the foreground with `SCCACHE_NO_DAEMON=1` and `SCCACHE_START_SERVER=1` on `ExecStart` only; takes the port from an already running server on start; `RestartSec=5`. Every compile handed to sccache therefore runs inside `builds.slice`. `OOMScoreAdjust=500`, so its compiles rank with the build steps. |
| `hana-ci.slice` | `MemoryMax=18G` only, `MemorySwapMax=2G`, no `MemoryHigh`. Runners `OOMPolicy=continue`. |
| CI slot pool | `/dev/steve-ci`, 14 slots, separate from the sessions' `/dev/steve` (31 slots). Runners: `CARGO_MAKEFLAGS=--jobserver-auth=fifo:/dev/steve-ci`, `BindPaths=-/dev/steve-ci`, `DeviceAllow` `char-rtc r` and `/dev/steve-ci rw`, ordered after `steve-ci.service`. No `CARGO_BUILD_JOBS`. |
| Build and CI kill order | Build steps and sccache at 500: each step's `builds.slice` scope sets `oom_score_adj=500` before starting the step, and `sccache.service` has `OOMScoreAdjust=500`. Session processes at 200 (rust-analyzer, builds outside `invoke.sh`). CI jobs at 100: `PIPELINE_JOB_OOMSCOREADJ=100` in the runners' `extraEnvironment`. earlyoom kills build steps first, then sessions' processes, then CI, the largest first within each level; the processes `--avoid` names go last. |
| Swap and earlyoom (`modules/linux/memory.nix`) | zram (zstd, 50%, priority 100), `vm.swappiness=100`. earlyoom decides on available RAM alone (SIGTERM at 5%, free-swap thresholds 100). Its score is roughly usage‰ of RAM plus swap, plus oom_score_adj, so the kill order comes from oom_score_adj. No `--prefer`; `--avoid` takes 300 from remote access, the desktop and the sessions themselves (`sshd`, `tailscaled`, kwin, plasmashell, `claude`, the tmux server and `herdr` among them). |
| Timers | `buildlog sample` every 60 s, `buildlog disk` every 600 s, `buildlog hourly` every 3600 s, disk-floor every 2 min (`sweep.py --floor-only`). |

The two ceilings (44G + 18G) deliberately exceed physical RAM together; decisions rest on kills and stall, not their sum.

On 2026-10-06 06:54 PDT, two hung hana tests in one local `verify.sh test` step held 11.4 GB and 15.5 GB; earlyoom first sent SIGTERM to 26 other processes, including six CI compilers (four hana CI jobs failed), and killed the tests last. `builds.slice` peaked at 37.7 GiB, under its 44G, because zram (10 GiB), sessions (8 GiB) and CI (3.4 GiB) had already taken the machine to earlyoom's 5% line.

### The memory gate (`scripts/lint/memory_gate.sh`, `scripts/lint/memory_admit.py`)

Sourced by `scripts/lint/invoke.sh` and by the BRP launch hook. A step starts when its expected memory fits beside current use and pending starts. The gate reads resident plus swap bytes from each running step's process tree. Historical peaks set the new step's need.

- **Rule** (`memory_admit.py` `decide`). Admit when running build charges plus `need + head_need` fit the 21 GiB build budget, `MemAvailable >= need + reserve + head_need + ramp growth`, and memory PSI `full avg10 <= 10.0`. `BUILDLOG_BUILD_BUDGET_GIB` sets a positive budget in GiB; an invalid value uses 21. Build anon at 16–20 GiB averaged 10.4% full PSI, rising to 16.4% at 20–24 GiB; the default moved from 20 to 21 on 2026-10-29 as a two-hour stability trial. During `RAMP_SECONDS` (120 s), a running step charges `max(promise, measured resident and swap bytes)`; after that it charges only measured bytes. Only ramping steps add `max(0, promise - measured)` to the memory floor. `reserve` is 5% of `MemTotal` (0 without a total). A step above the budget may run alone only when no head holds younger steps; it must still meet the memory floor and pressure limit. A dead or reused caller counts nothing. The oldest waiter is the head candidate. Before 600 s (10 min), younger steps may start when they fit on their own. At 600 s, or at once for a bumped waiter, the head takes priority when it fits now or `MemAvailable + measured >= head need + reserve`. Its next admission check records `holds_younger` in its waiter row. The row also records `priority_since`: younger steps wait for `STRICT_SECONDS` (600 s), may start on their own budget and memory checks for `BACKFILL_SECONDS` (120 s), then wait in the next strict window. The cycle ends when the head starts or leaves; a bump starts a new strict window. When no build runs, this head starts below the memory floor too; PSI above 10 still holds it. A bump changes the head order as before. Admission and queue display share `head_priority` and `queue_decision`; the head names the check that holds it through shared `head_wait_reason` and `head_wait_text`. Pressure takes precedence, then the build budget, then free memory; when both budget and free memory fail, it names both. The budget reason gives the build use at which the head can start. The oldest waiter also shows `younger steps may start until HH:MM` in the user's zone before 10 min, then `younger steps wait until HH:MM` or `younger steps may start until HH:MM` for the current window; queue and check wait lines share that text. Younger steps name a strict head. Pressure and available memory are read inside the check. `BUILDLOG_MEMORY_PRESSURE` changes the PSI path. An unreadable pressure file does not hold; the memory rule still applies.
- **Waiters** (`live_waiters`). A held step keeps `<pid>-<start>.waiting` in `admission/`. It records the caller identity, need, wait start and step label. Dead, reused or zombie callers leave the queue when read. The oldest caller is the head candidate. Younger steps may backfill until it has waited `HEAD_SECONDS` (600 s); a bump ends backfill at once. It takes priority when it fits now or when `MemAvailable + measured running bytes >= head need + reserve`; pending starts add no measured bytes to this test. From then on its row carries `holds_younger` and `priority_since`: younger steps wait in each 600 s strict window, then may start on their own checks in a 120 s backfill window. This repeats until the head starts or leaves; a bump starts a new strict window. A head that cannot fit even after the running steps end, and has no `holds_younger` flag yet, holds nothing from smaller steps. Admission and queue display use the same head rule. The head never charges its own need twice. Its check uses current measured memory and pending starts, so old peak promises cannot keep it waiting. Records from older callers get a label from their process folder and command. Both first and periodic wait lines name the head and its need when room is reserved for it; with zero running steps and a nonempty checker summary, they print that reason in place of the running-step counts.
- **`need`** (`expected_peak`). The first tier with at least 5 values in 14 days applies: this host and repository’s measured anon peaks (`admission/anon_peaks.jsonl`) of every test width, then build-log `peak_mem_bytes` x `ANON_SHARE` 0.65, then measured anon peaks of this step across repositories on the host, then the 12 GiB fallback. Repository identity is the normalized origin URL, or the oldest root commit when there is no origin; without either, only the fallback applies. `StepProfile` resolves identity for the estimate. A cached waiter must carry `repo_identity` (empty means unknown), `test_scope` and `estimated_at`; older rows resolve again. Waiting steps refresh identity and history every `HEAD_SECONDS` (600 s). Each answer updates the shell cache and waiter need. New anon rows carry `repo_identity` and `test_scope`; filtered tests and full runs use separate histories in every tier. Old anon rows mean full runs; build-log rows use their saved arguments. Package-only filter expressions and target selection count as full runs; test-name predicates, positional test names, skip and exact options count as filtered. Generic scratch names supply no old samples; old repository samples use the main checkout folder when it equals the origin repository name, including builds from its worktrees. Callers pass an explicit repository identity; the width report resolves hana from ~/rust/hana once per report. The pooled tier uses step and test scope across repositories, without a folder key. A missing index or history file skips that tier.
- **Ledger.** One `*.reservation` JSON file per admitted step under the build log's `admission/` directory (pid, pid start time, need, repo, step, worktree, admitted_at, sidecar path). Check, prune and write happen under one exclusive `flock` on `admission/lock`; a reservation whose pid is gone or reused is deleted when read. `MemAvailable` is read inside the lock, after the process readings.
- **`check` and `release`.** `check` returns a frozen `CheckResult` whose `reservation` is `Reserved(path)` or `NotReserved(held|launch|untracked)`. `StepProfile` (repo, step, worktree, peak) is resolved once per wait and passed back on later polls; each check reads one process table for all reservations while it holds the admission lock.
- **Queue API.** `/build:queue` reads the local session roster (`roster.roster(os.environ, roster.ThisMachine())`) once in a worker thread while `queue_view()` runs on the main thread, because the lock timeout uses a signal. Running is `# | Showrunner | Unit | Session | Step | Folder | Promised | Using | Delta | State`; Waiting is `# | Showrunner | Unit | Session | Step | Folder | Waiting since | Needs | Free | Reason`. Both tables take their labels from `roster.unit_labels` (`docs/as-built/session-roster.md`, "Unit labels"), matched by Claude session id or Codex thread id: Showrunner and Unit are short names (`builds`, `report`), never a long session name. An unmatched step keeps its recorded session name, else the folder basename, with `—` in Showrunner and Unit. When the roster read raises or returns problems, the tables still print, and one line after Totals says `Roster: <first problem>; Showrunner and Unit show — for unmatched steps`. `waiter_identity(step, worktree)` stores the bare step name, as reservations do, so Step is one word (`nextest`, `clippy`); `repository_name` keeps the repo. Free is `view.available` in GiB, or `—` when any waiter has `ReadingUnavailable`. The Reason omits the Needs and Free amounts. `build_queue.py` builds the head Reason from the `HeadAdmissionStatus` fields; `head_wait_text` remains unchanged for `verify.sh`'s memory wait lines. `queue_view()` waits up to 10 s for the shared admission lock, then reads the queue and one process table without subprocesses. On timeout it raises `TimeoutError`; `/build:queue` prints `admission lock busy for 10 s; try again` and exits 2. With no lock file it reads without a lock. `QueueView` holds waiting steps, running steps, available bytes, ramp growth, reserve and read time. Each running step keeps its historical promise and a `PromisedMemory`, `MeasuredMemory` or `GoneMemory` state. Admission and the view share `decide` for the build budget, memory floor and pressure limit. `NeedsBuildBudget` names charged builds and the budget. `NeedsMemory` carries `need`, `free`, `threshold`, `growth`, `reserve` and `head_need`; its Reason is `needs <threshold> GiB free: this step <need>, running steps may grow <growth>, head <head_need>, earlyoom <reserve>`, and a part that rounds to 0.0 is left out. `BehindHead` carries `head_name`, `head_since` and `head_session_id`; its Reason `behind <label> (waiting N min)` uses the head's Session label, and `head_name` is the label for an unmatched head. Other wait reasons are `HeadAdmissionStatus` (the head), `ReadyForAdmission`, `MemoryPressure` and `ReadingUnavailable`. A pressure reason names only the `full avg10` stall. Only a failed meminfo read gives an unavailable reason; the read changes no queue file.
- **Queue order.** `bump_waiter(selector, actor)` moves one waiter to the head under the admission lock. Select by 1-based position, session name or id, or full folder path or basename. `/build:queue bump` also resolves a unique shown Session label to its full session id; duplicate shown labels are ambiguous. Its result uses the shown Session label. Unknown or ambiguous selectors raise `ValueError` and move nothing. A bumped head starts first at the next check when memory fits. A separate `bump_order` field keeps its order through later polls; its original `since` and shown wait time stay unchanged. It holds later steps under the same head rule, including while measured steps finish to free its memory. Each bump writes one `queue_bump` row to the host's monthly build log, with actor, moved session, bare step, folder, old position and time. Index schema 22 adds `queue_bumps` for `buildlog query`.

`buildlog_wait_for_memory [ARGV...]` polls every `BUILDLOG_MEM_POLL_S` (5 s). A step with argv never starts without memory: at `BUILDLOG_MEM_WAIT_LIMIT_S` (900 s) it prints one notice and keeps waiting as a head candidate. The wait start is `BUILDLOG_MEM_WAIT_SINCE` when set, else now; the gate exports it as `BUILDLOG_MEM_WAIT_FROM` and passes it to `check` as the waiter's `since`, so a later pass of the same step keeps its place. A call with no argv (the BRP launch hook) uses the fallback `need` and writes no reservation. If its wait limit arrives without admission, it refuses the launch with status 2. It sets, in the calling shell:

- `BUILDLOG_MEM_OUTCOME`: `Granted` (explicit admission), `LeftQueue` (the call's leave hook selects another machine), or `CheckFailed` (the check cannot allow the step).
- `BUILDLOG_MEM_WAIT_S`: seconds from the first hold; 0 when it never waited.
- `BUILDLOG_MEM_RESERVATION`: the reservation path, empty when none was written. `buildlog_release_memory` deletes it.

Admission and hold checks fail closed. A missing script, a checker error, invalid output, an unreadable memory reading or an untracked admission stops the step with a non-zero status and one reason line. A reached launch wait limit also refuses the step. A check error cannot become a Mac retry or a Mac pass. Hold status 10 means wait or try an eligible Mac; status 75 from `wait-local` means its leave hook selected another machine. `wait-local` also returns 12 after it prints its refusal reason. Its statuses 10 and 12 stop the step with the same status and no added failure line when the check printed a reason. An absent reason or unreadable output adds the fail-closed reason, as do other check failures. Printed to stderr:

```
waiting for memory since HH:MM PDT: ...            (first hold: need, source, head, promised and measured GiB, running steps)
still waiting for memory (N min): ...              (every 60 s)
memory free after N min S s: starting
still waiting for memory after N min: this step is now first in line, and no build starts without memory
memory admission check failed (launch wait limit reached without admission); step refused
memory admission check failed (<last line of the Python output>); step refused
memory admission check failed (cannot read MemAvailable from <path>); step refused
memory admission check failed (invalid admission answer admit:untracked); step refused
build hold check register-local failed (exit 12); step refused
```

In `invoke.sh`, `run_once` checks natedev holds before memory admission, runs the gate for every step that compiles, recorded or not (`BUILDLOG_SCOPE=0` too), and rechecks the hold after every memory gate return: a new hold sends the call back to the hold waiter before its step starts. The hold recheck skips Python when the holder directory is missing or when the shell confirms that it is readable, searchable and empty. An unreadable directory still needs the Python check. It restarts the step's clock, then calls `buildlog_exec`. `buildlog_step_compiles` exempts `*/sweep.py`, `cargo [+toolchain] fmt` and `taplo`, which also skip the build-hold wait. `buildlog_exec` runs a recorded step with `systemd-run --user --scope --slice=builds.slice`. The scope's shell, `BUILDLOG_SCOPE_SH`, writes its marker, then runs `{ echo 500 > /proc/self/oom_score_adj; } 2>/dev/null || true;` before `"$@"`, so every process the step starts in the scope (cargo, build scripts, test binaries, any rustc or linker the step runs itself) inherits oom_score_adj 500; an unprivileged process may raise its own. Builds outside `invoke.sh` keep 200, and the Mac runs no scope. A Codex worker's detached run (`scripts/agents/mesh_runs.py supervise`) runs its whole command in a `builds.slice` scope the same way, with its own marker (`<run>.scope` beside the run log); no marker after the scope exits means the scope never ran it, and the command runs plainly. Its cargo builds call cargo directly, so before this they ran in `herdr-agents.service` at the sessions' CPU weight. `mesh_runs.py start` stores the tree key of its folder (`scripts/buildlog/treekey.py`) in the run record, and starts nothing when the worker already has a running record of the same command, folder and tree key whose pid is that record's `supervise` process (`/proc/<pid>/cmdline`); it prints that run's id, start time and log. Before this, a worker started one lint run three times on one tree after an interrupt (hana_catalyst-inspectors, 2026-10-21), and each run took memory, the cargo token and build time. A running record whose `supervise` process is gone (killed or crashed) delivered nothing, so `mesh_runs.py start`, `mesh_runs.py reap` and the worker's launcher (`codex_mesh._end_dead_runs`, which runs `reap` before it closes the inbox) mark it finished with `ended: supervisor gone` and deliver `Result: FAIL (no exit status)`; a dead record that a newer run of the same command in the same folder answers is marked finished and delivers nothing. `scripts/lint/test_invoke_scope.py` runs the extracted string under `/bin/sh -c` with fd 3 set as `buildlog_exec` sets it: step and child read 500, exit 7 passes through, and a failed write stays silent under an exported `SHELLOPTS=errexit`; the 500 checks skip when the runner already runs at 500 or more.

`BUILDLOG_SCOPE_SH` also writes the scope's cgroup directory to `"$BUILDLOG_PEAK.cgroup"`. `run_once` passes the step's argv to the gate and runs one `buildlog_sample_anon` sampler, which reads the scope's `anon` every second, keeps the maximum in the `.max` file beside the reservation, and exits when its parent is gone. `buildlog_finish_memory` stops the sampler, releases the reservation and removes the sidecar on every path; the release appends the maximum to `anon_peaks.jsonl` (host, repo, step, worktree, anon peak, exit status, UTC end time, `test_threads`, `call_id`), and nothing for an unscoped step. `scripts/lint/test_memory_admit.py` covers the rule, the ledger and the shell gate over a fake meminfo, index and cgroup tree; its shell tests run the gate under `set -e`, as `invoke.sh` does.

### Cargo wrapper (natedev only)

`scripts/build_hold/cargo` puts building cargo commands from shells, scripts and TUIs in a `builds.slice` scope. This includes `cargo mend`, which builds the workspace. It finds the first other cargo on PATH, keeps its arguments and exit status, and passes non-building commands such as `metadata`, `fmt` and `tree` through at once. A call already in `builds.slice` skips the hold check and a second scope. Other building calls check `hold_applies.py` when the hold directory has an entry: an applicable hold refuses the command; unreadable state prints a note and allows it. An empty hold directory starts no Python. Without a user bus or `systemd-run`, cargo runs directly.

Install on natedev from the repo root with `scripts/build_hold/install_cargo_wrapper.sh`. It links `~/.local/bin/cargo` to the wrapper and refuses to replace another file. `~/.local/bin` must precede `~/.cargo/bin` on PATH. On macOS, the installer makes no link and the wrapper calls cargo directly. Tests use `BUILD_HOLD_DIR`, `CARGO_WRAPPER_CGROUP_FILE` and `XDG_RUNTIME_DIR` to select temporary state.

### BRP launches

`scripts/hooks/pre-tool-use-brp-launch-gate.sh` is a `PreToolUse` hook on `mcp__brp__brp_launch` (`settings.json`, timeout 960 s). It sets `CLAUDE_CODE_SESSION_ID` from the hook input, clears the call id and asks `build_targets.py check-local` first. A launch from the session whose hold file is the only hold in force is admitted. A hold or unreadable hold state prints a deny answer with its reason and exits 0 without memory admission; the session launches again after release. An allowed launch runs the memory gate. A launch's build runs in the session's own scope, not `builds.slice`. A launch after release enters the memory gate without another release message.

### Memory kills in `verify.sh`

`run()` wraps `run_once`. A failed step is a memory kill when its output shows `SIGKILL|SIGTERM|signal: (9|15)` and the journal shows, inside the step's window, earlyoom's `sending SIG(TERM|KILL) to process` (`journalctl -u earlyoom`) or the kernel's `Memory cgroup out of memory` / `Out of memory: Killed` (`journalctl -k`). The query lives in `memory_kill_in_journal` so tests can stub `journalctl`. A memory kill is never the tree's failure: the step re-runs once (`killed for memory: <step>; retrying once`), and a second kill exits 137 with `killed for memory twice: <step>`. Each kill appends a byte to `MEM_KILL_FILE`; the second creates `<file>.stopped`. `note_event` passes `BUILDLOG_MEM_KILLS` and `BUILDLOG_MEM_KILL_STOPPED` to `record.py call`.

`verify.sh` also times the `cargo` board-token acquisition and passes it as `BUILDLOG_TOKEN_WAIT_S`. The clock is Bash's `$SECONDS`, or the integer in `UNIT_TOKEN_CLOCK_FILE` when set, so a test advances a file instead of sleeping. A wait that times out exits 1 before any call is recorded, so its time is in no row.

### Cargo token reclaim (`scripts/direct/board.sh`)

`verify.sh` acquires the board's `cargo` token with `--pid $$ --hold 3600` and no time limit: `acquire_token` repeats `--wait 3` (two tries 3 s apart) until the token is held, and adds the wait to the call's `token_wait_s`. The waits form one queue: a call tries only while no older call in the board's `token_waiters` folder still runs `verify.sh` (`count_token_waiters_ahead`, which also removes the files of ended calls), and `try_token_now` makes a wait when an older call waits. A call that gives the token back for a memory or hold wait waits again under its first start, in a file with an `.again` suffix, so it keeps its place and a newer call does not supersede it. The wait prints `waiting for the cargo token since <time>: <holder> holds it; calls ahead of this one: N`, a `still waiting` line every 5 min (`TOKEN_WAIT_NOTE_MIN`), and `took the cargo token after N min`. On 2026-10-22 about 25 calls polled one board's token, any of them took it when it came free, and two calls waited 3 and 3.5 h with logs that ended on "starting anyway", so their unit took them for dead. Each step gives the token back before `buildlog_wait_for_memory` and takes it again when the gate admits the step, so a peer builds while this run waits for memory; a step that leaves the wait for the Mac (`LeftQueue`) does not take it again. After admission the step tries the token once with `--wait 0` (`try_token_now`). When a peer holds it, the step gives its reservation back (`buildlog_release_memory 0`), waits for the token, and passes the gate again with the token held, so a step in the token queue promises no memory. The second pass sets `BUILDLOG_MEM_WAIT_SINCE` to the first pass's `BUILDLOG_MEM_WAIT_FROM`, so the step keeps its place in the waiter queue; `memory_wait` sums both passes. Kept reservations had promised 257 GiB that no build used on 2026-10-20, and every step waited the 15 min limit. The step's build hold wait (`build_hold_wait_local`, wrapped in `verify.sh`) does the same when a hold is present and the step holds the token: it gives the token back, waits out the hold, and takes it again, except after status 75 (left for the Mac). The hold time stays in the hold wait record; only the time to take the token again counts in `token_wait_s`. With no hold present, nothing is given back. The step runs in `run()`'s subshell, so its token wait reaches the call record through `TOKEN_WAIT_FILE`, and a token it gave back without taking it again leaves `TOKEN_WAIT_FILE.given_back`: `release_token` then counts the token as not held, so a call that ends after a Mac trip does not try to release a token a peer now holds (it only frees one a killed step took as its acquire returned). An INT, TERM or HUP during the token wait stops the waiting acquire and gives back a token it took in the last instant, and with `--pid N` `board.sh acquire` itself exits 4 (`gone <res>: pid N ended while it waited`) once N is gone. A step whose call is gone stops its token wait (`token_wait_orphaned`): each pass checks that the call's pid (`$$`) still runs, an acquire that exits 4 ends the wait too, and the step prints `verify.sh: the call that started this step is gone, so the step stops waiting for the cargo token.` and exits 1. On 2026-10-20 a test killed a call's group and left its step, which runs in a group of its own (`run()`'s `set -m`), trying again for 45 h with 15 GiB of deleted output still open; the test's cleanup now also ends every process in the call's session. A release moves the lock's `reclaimed_holders` lines whose holder still runs to `locks/<res>.reclaimed`, and the next acquire moves them back into its lock, so a reclaimed holder's late release still exits 3 after the token changed hands again. `board.sh acquire --pid N` (a positive integer, else exit 2) records N in `locks/<res>.d/holder_pid`. A waiter treats the token as stale when that process is gone, checked first, or when its hold has expired. Gone means `ps -p N -o stat=` exits 1 with empty output or reports a zombie; anything else, a failure of `ps` included, counts as alive, and a lock with no or a malformed `holder_pid` waits for expiry. So a `verify.sh` killed before its EXIT trap frees the token within one 3 s poll, posting `token cargo reclaimed from <holder>: holder pid <N> is gone`, while a manual holder is never reclaimed early. A newer call from the same worker, with the same verb and arguments in the same worktree (a lint key leaves out its package), ends an older one that still waits for its first token: each waiting call keeps `token_waiters/<slot>.<key>.<start>.<pid>` on the board, and a newer call sends SIGUSR1 to each older one whose pid still runs `verify.sh`. The older call gives back a token its acquire took in the last instant, prints `verify.sh: superseded by a newer <verb> call`, records outcome `superseded` and exits 76 (`VERIFY_SUPERSEDED_STATUS`); `mesh_runs.py` delivers that as `Result: SUPERSEDED (exit 76)`, not a failure, also when the run has a done message. A call whose acquire already won runs to the end, and a SIGUSR1 after the first wait does nothing. On 2026-10-21 one worker queued 27 calls this way, most on trees it had already left, and its peers waited up to 20 h for the token. Reclaiming a dead holder first SIGKILLs the step process group it recorded in `locks/<res>.d/owned` and fails closed (acquire exits 1, token left in place) when that group cannot be inspected or stopped; an expired hold whose holder is alive is reclaimed without touching its build. Reclaim and release run under an exclusive flock on `locks/<res>.guard`, taken by python3 `fcntl` on descriptor 9 (the Mac has no `flock(1)`) and dropped by the kernel when its holder dies: a reclaimer re-reads the lock under it, so two waiters cannot both reclaim and a release cannot remove a lock a reclaimer just made. Reclaim never waits for the guard; release retries for up to 10 s, then exits 1 (`board.sh: cannot guard <res> release`).

### Build log: records and schema

Index `SCHEMA_VERSION = 23` (`scripts/buildlog/index.py`; `open_for_update` rebuilds on a mismatch). Memory and coordination columns:

| Table | Column | Meaning |
| --- | --- | --- |
| `steps` | `mem_wait_s` | seconds the gate held the step (`BUILDLOG_MEM_WAIT_S`) |
| `steps` | `slice` | `builds` (scope ran), `fallback` (scope failed, ran without one), `none` (no scope tried) |
| `calls` | `token_wait_s` | cargo-token acquisition seconds; 0 when absent or not a whole number |
| `calls` | `mem_kills`, `mem_kill_stopped` | memory-killed attempts; 1 when a step was killed twice |
| `samples` | `builds_anon_bytes`, `ci_anon_bytes` | the `anon` line of each slice's `memory.stat` (process memory); NULL when absent |
| `samples` | `sccache_in_service` | 1 when `builds.slice/sccache.service/cgroup.procs` holds a process, 0 when empty, NULL without `builds.slice` |
| `memory_snapshots` | `src, host, at, slices, zram` | JSON slice counters and zram, indexed on `at` |
| `ci_jobs` | `run_state` | `JobRunState.RAN / SKIPPED / CARRIED_OVER` |

`steps.wait_s` keeps metadata and pass-record lookup time plus the ordinary build wait; `mem_wait_s` is memory admission. `calls.hold_wait_s` records held-target waiting separately, including each declined Mac retry, and `calls.target` names where the call ended. The Waiting table keeps `Held target` apart from `Memory admission`.

**Slice snapshots** (`scripts/buildlog/memory.py`). `buildlog snapshot`, and every `buildlog sample` (via `SampleTaken(at, host)` and `memory.write_snapshot(at, host)`), append a `memory_snapshot` record to the host's monthly samples file. Per slice (`builds`, `ci`, or `{"state": "absent"}`): `memory.events` `high`/`max`/`oom_kill`, `memory.peak`, `memory.swap.peak`, the three limits, and `memory.pressure` `some` total as `stall_some_us` (or `"unavailable"`); plus zram `mm_stat` data and compressed bytes. A snapshot failure prints `memory snapshot unavailable` and never fails the sample. `BUILDLOG_BUILDS_CGROUP`, `BUILDLOG_CI_CGROUP` and `BUILDLOG_ZRAM` point tests at fixture trees.

**CI jobs.** A job is `carried_over` when its attempt is above 1 and `started_at` precedes `created_at`, else `skipped` when its conclusion is `skipped`, else `ran`. Only `ran` rows store `duration_s` and `queued_s`; `queued_s` is `started_at - created_at` when both parse and the result is zero or more, else NULL. `elapsed_seconds(start, end) -> float | None` is unrounded; `seconds_between` rounds to 3 places. `ci_job_days` excludes `carried_over` and keys days by the run attempt's `started_at`.

**CI poll freshness** (`scripts/buildlog/ci.py`). Each poll that reached GitHub writes `<root>/ci/polled.json` `{repo: {polled_at, complete}}` atomically; a cold-credential skip or `GhError` writes nothing. `read_poll_state(repo) -> CompletedPoll(polled_at) | CappedPoll(polled_at) | NeverPolled()`; a malformed or zone-less stamp is `NeverPolled`.

**BRP launches** (`scripts/buildlog/launches.py`). `collect() -> LaunchCounts` turns each `brp_launch` result in `~/.claude/projects/*/*.jsonl` (`BUILDLOG_TRANSCRIPTS` replaces the root) into a `build` step with caller `brp-launch`: `ended_at` = `metadata.launch_timestamp`, `started_at` = that minus the launch duration, argv `cargo build --workspace --bin|--example <target> [--release]` (`--bin` only when `metadata.launched_as` is `app`), no memory fields. It reads `mcpMeta.structuredContent`, list `tool_result` items and `<task-notification><result>JSON</result>` strings, and skips any line lacking `brp_launch` or one of those markers before parsing. `launch_record(line, transcript, *, backfill=False) -> RecordedLaunch | LaunchOutcome` takes the location from `parameters.path`, else `metadata.working_directory`, else `LaunchOutcome.NO_LOCATION`; repo and worktree come only from `record.git_facts(location)`. Each launch is `launch-<sha256(session:timestamp)>.jsonl`, written only when absent (temporary file, hard link). `launches_state.json` holds each transcript's offset and marks; an entry without `reread_complete` is re-read once from the start, launches before its saved offset recorded with `branch` and `sha` null. `LaunchCounts.summary()` prints on stdout for `buildlog launches` and on stderr for `buildlog report`. `day_report` collects before `index.update()`.

**Window report** (`memory.window_report`), host-scoped (`store.host_name()`), times in PDT:

builds: high +N, max +N, oom_kill +N; stall +N.N s; peak X GiB, limit Y GiB; swap peak ...
CI: ...
memory waits: N steps, total T, longest L, K reached the 15-min limit | memory waits: none

Slice lines use the snapshots nearest each edge within `SNAPSHOT_DISTANCE_S` (120 s), else `<slice>: no snapshot within 2 min of <time>`. A counter that falls in the window is a reset: `<slice>: reset in the window; since the reset ...`. Edges round up to the next millisecond (`stored_bound`) to match stored records.

**Daily report** (`buildlog report [day]`, `scripts/buildlog/report.py`). Every step-based section counts natedev's steps only (`host = 'natedev'`); `### Mac` holds the Mac's (`docs/as-built/mac-test-offload.md`). Order: `## Builds, <day>`; `### Waiting`; `### Rebuilds` (where compile time goes; `docs/as-built/build-followups.md`, Rebuilds section); one section per kind; `### Memory pressure`; `### CPU and disk pressure` (`docs/as-built/buildlog-memory-stalls.md`); agent calls; test builds; `### Power profile` (`docs/as-built/build-targets.md`); Tests by target; `### Mac`; port-lint; `### CI`; `### Tests per edit`; Disk; summaries; one-line totals and notes.

- `### Waiting`: a `Wait | Longest | Over 5 min | Waited | Total | Worst` table, always present, in this order: `Build-folder turn, behind another worker`, `Build-folder turn, behind its own call`, `Held target`, `Memory admission`, `CI queue`. Held-target seconds come from `calls.hold_wait_s`; memory seconds from `steps.mem_wait_s`. `Longest` names who and its time; `Over 5 min` counts above 300 s; `Waited` is the count out of the day's population; `Total` is worker-hours or job-hours; `Worst` gives the top three. Each row uses `wait_row`; an empty kind reads `none`.
  - **Build-folder split.** `build_folder_waits(connection, day) -> (another_waits, own_waits)` returns two `ReportedWait` lists (`tuple[float, str, str, str]`: duration, owner, name, started_at), one entry per call in each, with the call's part of the wait as the duration and the worktree as owner and name. It reads the day's `tool = 'verify.sh'` calls and the token holders: verify.sh calls with a `unit_session` and an `ended_at` on the day or later. `token_holders()` turns each into `TokenHolder(call_id, unit_session, worker, starts_at, ends_at)` over `[started_at + wait_s, ended_at]`, grouped by session so each call scans only its own session's holders.
  - The cargo token is held per worker session, so only calls of the same `unit_session` can cause a token wait. A positive `token_wait_s` on a call with a session goes through `attribute_token_wait(call_id, unit_session, worker, starts_at, wait_s, token_wait_s, holders) -> TokenWaitAttribution(behind_another_worker_s, behind_own_call_s)`; a call with no `unit_session` puts its whole wait in the another-worker row.
  - `attribute_token_wait` takes the wait interval `[started_at + wait_s - token_wait_s, started_at + wait_s]` and splits it at the boundaries of the overlapping same-session holders other than the call itself. A segment is own only when every holder covering it has the call's worker; every other segment, uncovered included, counts as another worker. Own is capped at `token_wait_s`; another worker is the remainder.
  - A NULL worker reads `(unknown worker)`. Session calls with no worker never wait but can hold the token, and a worker waiting behind one counts as another worker.
- `### Memory pressure` always has its heading. It carries `memory waits: N steps, total T, longest L (<caller>)` or `memory waits: none`, the three instrument lines (sccache, unsliced steps, memory kills; natedev's samples, steps and calls only), the stall table, and `60 s samples: peak used memory X, peak swap Y; peak builds B, peak CI C (process memory); machine stall: ...` (`unavailable` per slice without samples).
- A `p95` follows every average: the kind tables (`COMMON_HEAD = Runs, Failed, Avg, p95, Range`; `COMMON_SQL` fetches `group_concat(duration_s)`), each `AverageColumn` (`<title> p95`), the summaries, Tests per edit (`p95 to next green`) and the CI queue clause. `nearest_rank(values, percent)` uses sorted index `(percent*n+99)//100-1` and also serves the Test builds p75 and the Rebuilds package p50 and p95.
- `### CI`: head `Workflow, Runs, Failed, Cancelled, Avg, p95, Range`; the summary names `<n> cancelled` only when nonzero. The queue clause is `jobs queued <avg> on average, p95 <p95>`, plus `, <N> without a known queue time left out` when any, or `no job has a known queue time` (`(<N> left out)`). Days key on the run attempt's `started_at`. Both CI summary paths end with `ci_freshness(day)`: `; CI never polled`, or `; CI recorded through <time>`, plus `, no poll since` when older than `min(now, day end) - CI_STALE_AFTER_S` (2 h) and `, the last poll was capped` for a capped poll.
- `brp-launch` steps show as `example launches (brp)`; launches from temporary folders group under their worktree, not as scratch (`GROUP_AS_SCRATCH`).
- The Mac note starts `Mac: sync paused since <time> (<why>).` while paused.

### Mac sync pause (`scripts/buildlog/sync.py`)

`buildlog sync pause <why>` writes `<root>/sync_paused.json` `{since, why}`; `resume` removes it. `sync()` holds an flock on `<root>/sync.lock` for its whole run; paused, it contacts nothing, prints `buildlog sync: paused since <time> (<why>); buildlog sync resume ends it`, returns 0 and leaves `sync.json` alone. `pause` takes the same lock (printing `buildlog sync: waiting for the running sync to finish`), so once it returns nothing contacts the Mac. `hourly` still polls CI while paused. `read_pause -> SyncPaused(since, why) | SyncRunning()`; `read_status -> SyncStatus(at, peer, ok, last_good: LastSynced | NeverSynced) | NeverSynced`. The reach check runs `mkdir -p <REMOTE_ROOT>; echo "rc=$?"` and judges the printed `rc=`; nonzero or missing (`reported rc=<n>` / `no rc= line in command output`) writes `sync.json` `ok: false` and exits 1. ssh exit 255 is a peer that did not answer (one line, exit 0). `rsync` keeps its exit-status checks.

### Build hold (`scripts/build_hold/build_hold.py`, `commands/build/hold.md`)

**Holder files.** One file per holder in `BUILD_HOLD_DIR` (default `~/.local/state/build-hold/`), one JSON line `{holder, since, for, release_eta, keep}`. `keep` holds PID/start-time pairs and defaults to empty for old files. Installed scripts refuse set directory variables or a changed `HOME`; unset the variable or use a shell with the user's home. The shell guard also refuses read-only `HOME`. The legacy free-text form reads, and an unreadable or malformed regular file stays a hold. Types include `HolderIdentity(key, name)`, `HoldState = NoHolders | ActiveHolders`, `Holder(name, since, purpose, release, key, keep)`, `ReleaseEta = KnownReleaseEta | UnknownReleaseEta`, and `ReleaseRequest = NoReleaseEta | ClockReleaseEta`. `write_hold` and `start_hold` take the resolved identity. Holder files supply state to status, dailies and Rust release checks. `natedev_holds(directory) -> NatedevHolds(in_force)` reads holder files once and never reads the cycle. Every present holder file is in force, even when the cycle has `released_at` or `release_started_at`. There is no releasing state. Only removal ends that holder's hold.

**Hold enforcer.** A holder file always means a hold; cycle release fields grant nothing. `hold_enforcer.py run` checks once a second. It reads the cheap process table once, then environments for processes owned by this user and arguments and cwd for candidates, their ancestors and call-id processes. A process with `BUILDLOG_CALL_ID` uses `step_record.read`: live states `on_mac`, `waiting_hold`, `waiting_mac` and `local_noncompiling` continue; `on_natedev` children stop during a non-holder hold. The live record’s controller PID and start time always continue so verify can route the step again. A missing, stale or unreadable record grants no permission. Only processes without a call id use command-name rules. It matches both argv and executable basenames, including absolute Rust toolchain, cargo bin and Nix paths, under direnv, systemd-run or a Codex sandbox. Runs include building cargo verbs (the shared set in `hold_applies.py`), nextest, compilers, clippy-driver, cargo-tile-real, session-owned rust-analyzer, Python unittest/pytest or test_*.py files, basedpyright, and shells running test_*.sh. Mac coordination scripts, version probes, cargo lookup verbs and basedpyright-langserver pass. The sole holder’s runs, its `--keep <pid>` list and descendants (PID and start time checked), user terminal or desktop app runs without agent ancestors or session markers, shared sccache-server work, and the enforcer and its ancestors may continue. A run from before `since` has no special permission. Every other run gets the holder and reason on stderr, best effort, then SIGTERM root first through descendants and SIGKILL for survivors after two seconds, with start time checked before each signal. A route state change does not cancel a pending kill for an already stopped identity. New Mac children stay protected. A release, sole-holder ownership or explicit keep still cancels that kill. Each stopped root writes a permanent `hold_build` row through the shared audit writer: schema 21 adds `action=audit|stopped`, with old rows read as audit. The row also carries the stopped root’s `call_id` from `BUILDLOG_CALL_ID`, or an empty value, so verify can find a stop after the hold ends. Its owning session registers for one release notice. `verify.sh` and `merge_gate.py` without a call id are never signalled: both wait at their own hold gates. With a call id, the record decides; verify routes eligible steps to the Mac and waits for other steps. Their running natedev test and type-check children still stop and write stopped rows with PID and start time; the merge gate can read those rows and rerun the stopped modules after release. No run is paused: cargo must release `/dev/steve` slots and locks, and wall-clock limits keep running. `hold` starts the user unit `build-hold-enforcer` with absolute paths, keeps an active unit, or starts a detached process without systemd-run or a user bus. `BUILD_HOLD_ENFORCER_DIR` holds its singleton lock; no paused record or thaw exists. `run` exits when no holder file remains. `scan` is read only and prints allowed, kept, or would stop, with owner, reason and pass time; status and the hold-start audit print kept runs and `--keep <pid>` for runs that would stop. A read-only pass after release on 2026-10-28 took 0.585030 s over 1,736 processes; this is one measurement, not a pass-time limit. Other users’ processes, such as the CI runner, are outside its reach; runs shorter than one pass can finish first, so call guards refuse those starts.

**Build call guard.** `settings.json` installs `scripts/hooks/pre-tool-use-build-hold-guard.sh` for Bash PreToolUse. The Bash front reads stdin once and starts no Python when the hold directory has no entry or the input has neither `cargo` nor `merge_gate`. An unreadable hold path also starts the decision reader. Otherwise it passes the same input to `pre-tool-use-build-hold-guard.py` and relays its output and status. The guard refuses raw building `cargo` verbs (including short forms and `+toolchain`) while a non-holder natedev hold applies; removal ends that holder’s hold. All `verify.sh` calls pass, with or without a step record: verify routes eligible steps to the Mac during the hold and waits for other steps. Non-building calls pass. The Python guard checks the command through `tool_call_text.py`, checks for a hold entry, then imports `scripts/build_hold/hold_applies.py` in the same process. The helper uses `target_state(local_target())`, `natedev_holds` and `caller_holds_only_own()`. The sole in-force holder may build. Other sessions see `natedev builds are held by <holder>. Keep working, writes included. Use verify.sh: eligible steps go to the Mac; other steps wait. Raw cargo and merge gates must wait for the hold to end.` Only in-force holders are named, with `holder_text`. The helper exits 0 with that refusal on stdout, 1 silently when builds may run, or 2 with a read error on stderr. The guard denies hold read errors and any other exception in its decision path with a one-line reason that names the failed read. Only an explicit allow decision permits a build; no wait is registered.
The cargo verbs include `mend` and `miri`; the guard does not match `verify.sh` step names or options.
The guard also refuses `merge_gate.py` in every mode, called directly, through Python or through `lib/py`, with the same hold decision; its refusal says the gate waits for the hold to end and to run it after the release. Quoted mentions and written examples pass. Codex workers get the same Bash front and guard through `scripts/hooks/codex_hooks.py`; unit run markers let workers of the sole holder build.

**Build audit.** `audit_builds(proc_root, holders, buildlog_root)` reads `cargo-tile-real`, `cargo`, `cargo-nextest`, `rustc` and `rustdoc`. One top cargo or nextest process is one build. Nested cargo, nextest and compiler processes are its children, including through a shell. A compiler with no cargo ancestor is a separate build. The audit reads each process start time before and after its other files. It checks the process and its ancestors again before classification. A parent with a later start time cannot own an earlier child. An unreadable environment does not remove the build from the audit.

The owner comes from the process or an ancestor: `CLAUDE_CODE_SESSION_ID`, a unit run mapped through `owning_session(environment)`, or `CODEX_THREAD_ID`, else its nearest `claude` or `codex` ancestor. An agent without a session id is identified by its command, PID and start time. `holder` uses the same holder file key rule as `caller_holds_only_own`: that session's hold must be the only hold in force. `admitted` means the build is in the `builds.slice` cgroup used by `invoke.sh`, or the build or an ancestor has a matching PID and start time in the memory gate's `buildlog/admission/*.reservation` records. The audit reads these records without changing them. An inherited verify call id alone does not prove admission. The other classes are `other_session` and `no_session`. These audit classes describe ownership and memory records; the enforcer applies its allow rules separately. The printed audit omits `no_session` builds. The audit sends no messages and stops no processes. `hold`, `status` and `audit` accept `--proc-root` for a fake process tree in tests.

The audit calls `hold_enforcer.record_build(..., action="audit")` for each `other_session` or `no_session` build. The enforcer uses the same writer with `action="stopped"` for each stopped root. Both call `store.append_line` in the current process, after the audit read; no detached audit recorder runs. The kernel boot id, PID and process start time identify the build. The permanent file is `buildlog/<host>/hold-builds-<hold hash>.jsonl`. A separate `.lock` file covers the duplicate check and append, once per build, holder key, `since` and action. A new hold or a reused PID gets a new row. Index schema 21 adds `action` to `hold_builds`; old rows read as `audit`. Rows record hold identity, build identity, class, owner, command as shell text, working directory and observation time. Holder and admitted builds get no audit row.

**Holder key (2026-10-08).** A hold file is named by the holder's Claude session id: the caller's (`CLAUDE_CODE_SESSION_ID`) when `--holder` is left out, else the live session `--holder` means (`sessions.addressed`: its name now, or a name it alone once had). `Holder.key` is that file name and `Holder.name` is the session's name now, looked up at each read; the `holder` field in the file is the name at hold time and is shown only while the session is not live. `cycle["holders"]` keeps the key given to `start_hold`; `holder_path` replaces unsafe characters to make `Holder.key`, the file name. Different keys can name the same file, so a recorded release matches both that file name and its `since` instant. A holder that is no live Claude session keeps its name as the key. `held_key` finds a hold taken under a name before this change by the name given, the session's name now and its former names.

**Hold cycle.** `BUILD_HOLD_RELEASE_DIR` defaults to `~/.local/state/build-hold-release`, outside the holder directory. `current` names `<id>/cycle.json`, atomically replaced under `release.lock`. `HoldCycle` stores its id, open time, holders with `{since, released_at}`, recipients by session id, release start and `ReleaseEntry` rows with session id, name and delivery outcome. The first hold with no files opens a cycle without reading an old one. With other holders it joins the cycle; without a readable cycle it writes its file and opens none. Old cycle files with call, generation and gate fields still read; those fields no longer control a build.

**Release** (`release_cycle`). Under `release.lock`, `release_hold` first removes the holder file and queues the `ended` event. Only then does `release_cycle` record the holder's `released_at`. With another holder file present it prints `released; still held by <holder> (for ..., release eta ...)` and sends no notice. After the last file is gone it records `release_started_at` and sends notices. A stopped release leaves either a present file that still holds, or no file and a released hold; cycle fields grant nothing. All `wait-local` calls can then return and enter their memory gates. No waiter acknowledgement or turn can delay release. The memory gate orders the builds and starts each only when memory is available.

After the file is gone, `notify_release` sends one notice to each recorded recipient: start builds and BRP launches now; the memory gate orders them. No answer is needed. Each attempt is saved before sending, so a stopped sender does not repeat a notice. `socket_for` returns `RecipientLive | RecipientGone | RecipientLookupFailed`; lookup exit 1 means gone, other failures retry three times with one second between tries. Send exit 0 is delivered, 1 queued but unconfirmed, other failed. `Not reached, tell them yourself: <session name> (<reason>)` names failed, gone and unconfirmed deliveries. `cycle_status_lines` prints delivery outcomes. Release waits for no answer, build or memory allocation.

`release --resume` supports a file left by an old release. It refuses while any hold is in force. With no cycle, the holder broadcasts the release. `open_cycle`, `save_cycle` and `write_hold` write a complete temporary file before `os.replace`; holder temporary files stay outside the holder directory.

**Damaged record.** `read_cycle` validates the `HoldCycle` shape, session identities and delivery outcomes and requires each holder's `since` to be an instant with an offset; it raises `ReleaseRecordReadError` (a `ValueError`) naming the fault. An invalid holder time follows the same recovery path as any other unreadable record. Changing commands read through `read_cycle_for_change() -> HoldCycle | NoCycle | DamagedRecordSetAside(path)` under the lock: on damage it renames `cycle.json` (when it exists or is a dangling symlink), else `current`, to `<name>.damaged-<UTC YYYYMMDDTHHMMSSZ>` (`-2`, `-3`... when taken), removes `current`, and prints `release record could not be read (<error>); set aside as <path>; this hold now releases every session at once`. Read-only `status` and the dailies footer print `release record could not be read: <error>; /build:hold release sets it aside and ends the hold` and change nothing.

**Recorded hold intervals.** A new holder file queues a `began` event after writing the file; every removal in `release_hold` queues `ended`, using that file's key, name and reason. Repeating a hold writes no event. The event's UTC `at` is taken under the coordination lock and queued there; a detached `record.py hold-event` starts after the lock closes. A stalled event log cannot delay hold or release. Both reports read current coordination state independently. A lost event reads `end not recorded` or `began not recorded`, never a changed hold. The index keeps one row per event with its source file; the `holds` view pairs by host, target and key, ordering equal instants began first. Overlapping holders count once in held duration. A present holder file keeps an interval with no recorded end open, regardless of cycle release fields. Times shown use the user's zone, stored instants UTC.

**Target option.** `--target` on hold and release defaults to natedev and is decoded into `NatedevHoldTarget | MacHoldTarget | UnknownHoldTarget | UncheckedHoldTarget`. Only a name other than natedev or mac reads the config, through `read_targets` imported at module level from `scripts/build_targets/target_config.py`; a readable config answers with the configured targets, an unreadable one with `unknown target <name>; the target config cannot be read: <reason>`, and both exit 2. The Mac subprocess is found beside build_hold via `Path(__file__)`, runs with `sys.executable`, and returns `MacHoldResult(status, stdout, stderr)`. ### Broadcasts to sessions (`scripts/message/top_level.py`, `commands/notify_top_level.md`)

`top_level.py` takes no arguments (any argument: `usage: top_level.py`, exit 2) and runs no ssh. `forwarded_sessions()` reads this machine's roster (`roster.roster(os.environ, roster.ThisMachine())`, `docs/as-built/session-roster.md`) and keeps each `roster.is_top_level` row: a Claude session that is neither a worker nor a unit director under a showrunner, so a unit director with no running showrunner is included. Roster problems print on stderr as `top_level: roster: <problem>` and the rest still prints. Each row's socket comes from the newest running record for its session id (`sessions.running_sessions()`), so a conversation two processes hold (resumed in a terminal while the desktop app still has it open; seen 2026-10-08 as `bevy_brp` listed twice) is listed once, and two sessions that share only a name are both listed. Each row becomes `AddressableSession(name, session_id, address) | UnaddressableSession(name, session_id)`. Only addressable sessions print, one `<name>\tuds:<messagingSocketPath>` line each, sorted by name then address, and are recorded as hold recipients (`build_hold.py record-recipient`; `main` returns 1 when a record fails); each unaddressable one prints `not reachable: <name> [<session id>] has no messaging socket` on stderr. `/notify_top_level` sends to each `uds:` address, adds every ListAgents peer on another machine unless `--here`, asks showrunners to pass the message to their unit directors, names held or refused deliveries by name and address, and reports each `not reachable` line as a session not told.

- Holds: `read_dailies_hold()` reads the holder files. Report and `--footer` print one line per holder with its purpose, start and release ETA. ### Disk floor: what it removes (`scripts/lint/sweep.py`)

While `/` has less free than `sweep_free_floor_gib.<host>` in `config/lint.conf` (300 GiB on natedev), `hold_floor` removes build output from the cargo target directories under `FLOOR_ROOTS` that no build holds. It removes only the shortfall (`budget = total - (floor - scanned_free)`, with `scanned_free` read after the scan that measures the caches, so space another process frees during the scan is not taken again; at or above the floor after the scan it takes nothing), from idle targets in last-use order, oldest first, across all locations (`/tmp` targets have no special priority; `build-targets.md` → Build output retained by the sweep):

- **What a target is.** `is_cargo_target(directory)`: a directory holding `.rustc_info.json`, or cargo's `CACHEDIR.TAG` (matched on its line `# This file is a cache directory tag created by cargo.`) beside a build tree (`build_trees`). `target_dirs()` and `disk.py`'s `outside_directory_bytes()` both call it. Either marker alone misses targets: into a folder cargo creates, the tag and `debug/` appear at once and `.rustc_info.json` comes when the first build ends, or never; into a folder that already exists (mend's wrapper makes hana worktrees' first) cargo writes `.rustc_info.json` early and no tag.
- **Targets in use.** A target whose cargo locks a build holds is busy, and so is one a live process uses (`process_uses`, 2026-10-15): its `/proc/<pid>/exe`, `cwd` or a `maps` file lies under the target, or it is a cargo-nextest run (`nextest` as its first argument, or argv[0] `cargo-nextest`) whose `--target-dir`, `CARGO_TARGET_DIR`, or else the directory beside a target that holds its cwd, names it. nextest's run phase holds no cargo lock and executes binaries from `deps/`; a floor sweep at test 2105 of 4072 left 1965 hana tests failing to exec. `hold_floor` prints `lint sweep: pid <pid> <how>; <target> left alone` and counts it with the held targets; `sweep_workspace` prints `… skipped` and sweeps nothing. A running app keeps its target too. An exe or mapped file that reads `(deleted)` is no use (2026-10-21): the sweep can neither take nor break it, so a stale process whose exe and mappings under a target are all deleted, with its `cwd` outside, leaves the target idle (a hung `cargo-berth resolve` had held 26 GiB of cargo-liner-berth's target for three days). One scan of `/proc` covers every target (0.21 s over 110 targets and about 600 readable processes); it runs only below the floor. Without `/proc` (the Mac) nothing counts as in use.
- **Roots.** `FLOOR_ROOTS` is `~/rust`, `~/.local/state`, `~/.cache` and `/tmp`. `~/.cache` came in on 2026-10-21, after 421 GiB of idle targets under `~/.cache/trace-targets` had stayed unseen; it adds 0.4 s to the walk (21,000 folders). `~/.cache/sccache` holds no `.rustc_info.json` and no cargo tag, so it is never a target.
- **Agent scratch under /tmp.** `sweep.py --floor-only` calls `tmp_sweep.run_if_due` before `hold_floor`, so idle scratch goes before any build cache. It runs the sweep when `tmp-sweep.stamp` in the lint-sweep state folder is an hour old or more (`RUN_INTERVAL_SECONDS`). The stamp moves before the run, so a failed run also waits an hour. `tmp_sweep.py [--dry-run]` runs it at once. For hand cleanup, run `tmp_sweep.py --plan <new-plan.json>` to list every candidate with `keep` or `remove` and one reason, and save the plan without deleting anything. Then run `tmp_sweep.py --apply <plan.json>`; it judges every candidate again once, at its start, with the timed sweep's ownership and process-use checks, keeps planned paths that gained a keep reason, and logs each removal. It never deletes an unplanned path. Hand cleanup also requires end evidence: all recorded workers ended, an expired scratch task, or a recorded verify run that stopped. Age alone does not permit hand cleanup. On the Mac, which has no disk-floor job, the hourly `tmp-sweep` job (nixos `modules/darwin/tmp-sweep.nix`) runs `tmp_sweep.py`. The roots are the same on both machines, each by its real path, because the Mac's /tmp is a link to /private/tmp and lsof prints real paths. They are `/tmp/claude`, `/tmp/claude/delegate`, `/tmp/claude/unit`, each `-`-prefixed project folder in every `/tmp/claude-<uid>` this user owns (so Claude Code's own `bash-edit-diff/` stays), the scratch root `/tmp/claude/scratch` (one entry per task folder; a change review row's folder stays until its verdict), and the temp folders: /tmp, `$TMPDIR` and the Mac's `CS_DARWIN_USER_TEMP_DIR`. In a temp folder only a tempfile folder and a `lint/invoke.sh` log file (`INVOKE_TEMP_NAME`: `lint_invoke.*.log`, `buildlog.*.log`, `.peak` and `.peak.cgroup`; a killed run leaves them, and natedev /tmp held 1,308 and 1,438 on 2026-10-27) are judged. A tempfile folder (`TEMPFILE_NAME`) is `.tmp` and 6 letters or digits (Rust's tempfile crate), `tmp.` and 8 to 10 letters or digits (mktemp), or `tmp` and 8 lower-case letters, digits or `_` (Python's tempfile), the names test runs leave behind (natedev /tmp held 2,662 Rust ones on 2026-10-26 and the Mac's temp folder 273; the first folder audit that day found 3,917 mktemp and Python ones). In /tmp alone (the wide root; `$TMPDIR` and the Mac's temp folder hold app state, and macOS clears its own) every other empty folder this user owns is judged too, whatever its name, and goes after 7 idle days (`WIDE_IDLE_SECONDS`) with the same in-use check. A folder that holds only folders, however deep, counts as empty (`holds_no_file`; a tree of more than 1,000 folders does not), and its idle time is the newest mtime in the tree (2026-10-27: 155 nix-shell folders of empty `hana-runtime` folders stayed). A `direct/verify.sh` run folder (`VERIFY_TEMP_NAME`: `verify-hold.<pid>.XXXXXX`, with the run's `verify-copy.<pid>.XXXXXX` folders inside it) is judged in every temp folder. Its EXIT trap removes it, but a killed run leaves it (natedev /tmp held 47 hold and 6 copy folders on 2026-10-27). It stays while the named pid runs `verify.sh` (a `verify.sh` argument in `/proc/<pid>/cmdline`, or `ps` on the Mac) and that process started no later than the folder's mtime, so a reused pid does not keep it; otherwise it goes at the next run. An old name with no pid takes the 4-hour rule. A folder there that holds something can hold work, so the folder audit judges it, with a git check first (2026-10-27; until then the sweep took any idle folder, and on 2026-10-26 1,103 month-old ones went by hand, an rm the user had to approve). A folder a system tool owns stays (`SYSTEM_TEMP_NAMES`: `claude`, `.X11-unix` and the other X folders; `SYSTEM_TEMP_PREFIXES`: `systemd-private-`, `tmux-`, `nix-`, `ssh-`, `claude-`, `com.apple.`, `powerlog`), except an empty `nix-` one (`EMPTY_PREFIXES`: nix-shell and nix develop leave theirs, 1,321 in natedev /tmp on 2026-10-27), as do another root and a folder that holds one. The sweep does not judge or log other entries in a temp folder. An entry is one top-level file, folder or link under a root. It goes when nothing in it changed in 4 hours (`IDLE_SECONDS`) and no process has its cwd, an open file or a mapped file in it (one `/proc` scan per run; where there is no `/proc`, one `lsof -n -P -w -F pfn` scan: `cwd`, open files, and `txt`/`mem` mapped files). A change is the newer of mtime and ctime, over everything inside the entry, except a folder's ctime in a temp folder or a session or run temp root (systemd-tmpfiles-clean moves it daily). The entry's own times count only for a file, a link or an empty folder. These stay: the roots and both `active/` run-marker folders with every marker in them; a run folder under `unit/` or `delegate/` named by any active marker, with any `mesh_roster.json` worker not ended (paused included), or whose `progress_history_state.json` worktree belongs to a live session or a paused session in the shutdown mover's records; these runs and their temp entries stay even when their director process stops. A running director recorded in `director` or the opening `run_started` history event also keeps the run. A kept run also keeps any folder that contains a `mesh_runs/*.json` record's `cwd`, or is that working folder. Only these records name worker folders; pending files are not read. An empty mesh run file is not a record. Each roster thread whose worker is not ended keeps its `/tmp/claude/session/<thread_id>` parent; old entries inside that parent still take the 4-hour rule. An unreadable non-empty mesh run record keeps scratch entries and top-level `/tmp/claude` entries and prints its path. It does not keep old temp entries in session roots. Before deleting an idle entry under any root, both timed and hand cleanup check for git worktrees down to three folder levels, without following links. Uncommitted changes, untracked files, a stash or commits absent from remote and local clone-source refs keep the entry. Git checks use `GIT_OPTIONAL_LOCKS=0`, a 10-second timeout per command, and never fetch. A failed check keeps the entry. The folder audit uses the same git check. The new reasons `a live worker uses it` and `it holds unsaved git work` include kept paths in the log. Any unreadable marker, roster, session, shutdown or run ownership record keeps the affected runs; a session folder named for a running session, though an entry of 1 GiB or more in its `scratchpad/` and `tasks/` is judged like any other (`SESSION_ENTRY_MIN_BYTES`; showrunner, 2026-10-25: a live session keeps small files there that it only reads, and a read does not move mtime); each of these when a session record cannot be read; an entry that cannot be read; and everything when neither `/proc` nor lsof can show which processes use the entries. Links are never followed, a read-only folder is made writable and deleted, and a project folder left empty goes. Each run appends one JSON line to `~/.local/state/lint-sweep/tmp-sweep.jsonl`: `deleted` (path, GiB, last change), `freed_gib`, `failed`, `kept` (a count per reason), and `kept_paths` (every reason except a recent change and a small entry in a running session's folder; an in-use path names its pid and how it uses the entry). Lines older than 7 days drop off. The sweep is the only remover under its roots: `disk-floor.nix` excludes `/tmp/claude` and `/tmp/claude-*` from systemd-tmpfiles' age cleanup (`x` rules). Its `q /tmp 10d` rule deletes each file in /tmp older than 10 days, and then each empty folder. On 2026-10-26 that rule had removed an idle unit's run folder and its run marker, one file at a time. The run also prints one line per deletion and a summary to the disk-floor journal. History: it replaced `remove_session_scratch` (2026-10-21: ended sessions only, 24 h idle) on 2026-10-25. That day /tmp/claude held 122 GiB and /tmp/claude-1000 held 86 GiB, and a one-time cleanup had deleted both `active/` folders. The first dry run, with the 1 GiB line, would delete 1,891 entries (20.4 GiB) in about 4 s. The rest stayed because processes used the entries (a 70 GiB target) or because running sessions and unit runs held them.
- **Use stamp.** `sweep_workspace()` sets the mtime of `.lint-sweep-used` (`USE_STAMP`) in every root `cargo_roots()` returns, before `lock_trees`, so a step that compiled nothing, or whose sweep was skipped because a build held a lock, still counts as use. A dry run and `--target-dir` (CI) write none; a write failure is ignored.
- **Target last use.** `target_last_use(root, groups)` is the newest of the stamp's mtime and the target's build units' `last_used`.
- **Order.** `shrink()` and `choose()` take a `RemovalOrder`, a sort key over `Group`; the smallest key goes first. The workspace budget sweep passes `unit_age` (most whole days unused, then oldest compile). The floor passes the target's last use, then `unit_age`: the least recently used idle target loses output first, wherever it is, until the shortfall is met, then the next one. `recent_minutes=60` in `[sweep]` of `config/lint.conf` puts targets used in the last hour after all older targets. This is a lower eviction priority, not full protection: recent output can go when older output cannot meet the floor. A scratch target a build holds is left like any held target. Orphaned files (`Scan.orphans`, one group per build tree) go first from any idle target, whatever the order.
- **Lines.** After the removal lines, one line per target that lost output, largest first: `lint sweep: the floor took <gib> from <target>, last used <when>` (`would take` on a dry run). Orphan bytes count toward their target, and a group whose removal failed is left out, so each line is GiB actually taken. The removal line's `last used <oldest> to <newest>` spans the oldest and newest unit among those chosen.

On natedev (2026-10-08) the target rule finds 76 targets where `.rustc_info.json` alone found 41: all 35 added are scratch folders under `/tmp`, 31 of them finished builds carrying only the tag, and five under `/tmp/ct-g1l`, outside both Claude temp folders. The walk takes 2.2 s (1.5 s before).

Measured over the 24 h after the target-first order went live (2026-10-06 16:33 PDT, 300 GiB floor): the 2-minute timer took 84.0 GiB in 17 sweeps, 98.3% of it from targets idle over 6 h, and the newest unit a sweep took was last used a median 15.2 h earlier. The 24 h before, under the old order by build unit and almost all at a 500 GiB floor: 870.1 GiB in 155 sweeps, median 3.3 h. The two days differ in floor as well as order, and the memory gate above went live 85 minutes into the second.

### Scratch folders (`scripts/lib/scratch.py`, `scripts/hooks/pre-tool-use-scratch-guard.py`)

Agents made loose repo copies, repros and test trees in /tmp and ~/rust, and nothing removed them; sessions run for weeks, so a session end is no cleanup point (user, 2026-10-26/27). Each scratch folder now belongs to a task, and the task's end removes it. `scratch.py new [--task <task> | --until <when>] [--name <word>] [--visible]` makes one and prints its path; `adopt`, `hold`, `release`, `renew`, `end` and `list` do the rest. A task is `run:<run id>`, which `end_session.sh` ends; `phase:<unit>/<phase>`, which `merge_checkpoint.py` ends after it records the phase's code checkpoint; `gate:<id>`, which the gate's caller ends; `row:<showrunner>-C<n>`, which `change_review.py verdict` ends whichever way the verdict goes; or `until:<time>` (`--until YYYY-MM-DD [HH:MM]`), which the hourly tmp sweep ends when the time passes. With no task a folder lasts 24 h. The sweep keeps a task's folder while the task is open and removes any after 7 idle days. `scratch.py hold <path> --reason <why>` (or `change_review.py add --hold <path>`) keeps a folder where it is until its task ends, recorded in `~/.local/state/scratch/holds.json`; `end` removes it then, unless a repo in it holds work on no remote (uncommitted changes, a stash, commits on no remote), which stays with its hold marked ended. A folder is `/tmp/claude/scratch/<kind>-<name>-<word>-<6 chars>`; `--visible` (rows only) puts it at `~/rust/repro/<showrunner>-C<n>-<word>`, where cargo-port lists it. Each holds `.scratch.json` with its task, maker session and times. A git worktree goes through `git worktree remove`. A failed removal warns and never fails the merge or the verdict.

The scratch guard, a `PreToolUse` hook on `Bash` for Claude Code (`settings.json`) and Codex (`codex_hooks.py`), refuses a command that makes a new folder directly in /tmp, `$TMPDIR`, /tmp/claude, ~/rust or ~/rust/scratch (and judges a Write or NotebookEdit file path where its matcher names them): mkdir, mktemp -d, git clone, git worktree add, cp -r/-R/-a, rsync, cargo new/init, and tar extraction into a root. Allowed there: the session scratchpads (`/tmp/claude-<uid>`), `/tmp/claude/unit`, `/tmp/claude/delegate`, `/tmp/claude/session` and both scratch roots; ~/worktrees is no root, and a `make_a_worktree` command is never judged. A heredoc body, a quoted argument and a comment are data. A path the hook cannot follow (a variable other than HOME or TMPDIR, a command substitution, a command inside `bash -c` or ssh) is allowed, and the hourly tmp sweep is the backstop. A `TMPDIR` inside a session scratchpad, a session temp root or a run folder is no root.
Before its checks, the scratch guard uses the session-start path helper to restore only the input session id's missing temp folder with mode `0700`; an existing folder costs one `os.stat`, a missing or invalid id creates nothing, and a repair error allows the tool call to proceed to the checks.

Each Claude session's `TMPDIR` is `/tmp/claude/session/<session id>`: `hooks/session-start-temp-root.py` makes it at start, resume, clear and compact, and writes `export TMPDIR=...` to `$CLAUDE_ENV_FILE`. A run's workers, its codex app-server (`codex_mesh.py`) and `verify.sh --session-dir` use `<run folder>/tmp`. So mktemp, tempfile and Rust `.tmpXXXXXX` folders land there, and the hourly tmp sweep judges each entry with its 4 h rule; the root goes only once its session or director stops, and nothing waits on that. In /tmp and the other temp folders a folder's ctime is no change, since `systemd-tmpfiles-clean` moves it every day (its 26 Oct run kept month-old folders such as `cargo-installQOkrzS` looking fresh to the 7-day rule).

The daily folder audit (`scripts/lint/folder_audit.py --send`, a `nate.jobs` job on natedev and on the Mac) is the backstop for loose folders that can hold work: ~/rust, ~/rust/scratch, and the /tmp, /tmp/claude and `$TMPDIR` folders the sweep leaves. A folder in ~/rust is loose when its name is not in `config/rust_roots.txt` (one list for both machines) and it is not `repro` or `scratch`; every folder in ~/rust/scratch is loose, since `scratch.py` never makes one there; a folder in /tmp, /tmp/claude or `$TMPDIR` is loose when it is no session scratchpad, scratch root, run folder root, tempfile folder, `verify.sh` run folder or folder that holds only folders (the sweep judges those) or name a system tool owns. When `config/rust_roots.txt` cannot be read (an old checkout), nothing in ~/rust is judged. Only folders this user owns that did not change for a day count. Idle time comes from the newest mtime of the folder and of what is in it down to 3 folders (`target/`, `node_modules/` and `.git/` passed over), and of each git repo's `HEAD`, `index` and `logs/HEAD`, so a commit counts; ctime never counts. A folder with more than 50,000 entries in that depth stays and is named. A loose folder idle 7 days (`REMOVE_AFTER_SECONDS`) is removed when no open hold names it, a folder in it or a folder that holds it; no process works in it or has a file in it open or mapped (the sweep's `/proc` or lsof scan); no socket in it is bound by a live process (`/proc/net/unix`; on the Mac any socket keeps it); and no git repo in it holds work on no remote (`scratch.unsaved_work`: uncommitted changes, a stash, commits on no remote, or a repo git cannot read). A removed linked worktree is pruned from its source repo, and each removal appends a line to `~/.local/state/folder-sweep/removed.jsonl`. It removes only once armed: `folder_audit.py arm` writes `~/.local/state/folder-sweep/armed` and `disarm` removes it; until then each line says `would remove`. Its first dry runs (2026-10-27) found 106 loose folders on natedev, 36 to remove (all old /tmp leftovers), and 13 on the Mac, 8 to remove (mostly ~/rust/scratch). The maker is the earliest-started session whose transcript holds a command (a JSON `"command"` string) that names the folder, since a listing in a command's output names every folder it shows, found in one ripgrep pass over all transcripts (about 6 s over 22 GB; a Python scan took 4 h 24 min); the name must end at a path boundary. Each maker gets one message that lists its folders with what happened to each and names `scratch.py adopt` and `scratch.py hold`; a folder no transcript names is printed only.

### Disk-floor alerts (`scripts/lint/sweep.py`, `scripts/buildlog/disk.py`)

`hold_floor` writes `floor.json` in `${LINT_SWEEP_STATE_DIR:-~/.local/state/lint-sweep}` under `FLOOR_LOCK` after each floor sweep: time, free bytes, build-cache bytes (idle and busy target dirs plus both CI runner trees), `last_alert_at` and `last_push_at`. After a non-dry sweep it sends at most one alert:

- **Floor out of reach** (every removable unit chosen, still `left > budget`, and free space under the floor after removals), on its own hour (`push_history`). It never asks the user to free space by hand (2026-10-21). `floor_holders` names each busy target with its size, the pid that holds it (`process_uses`, or for a held cargo lock `lock_holder` from `/proc/locks`, read up to `PROC_LOCKS_READS` (3) times before it answers no holder, because under load one read can skip a line) and that pid's Claude session (`holder_sessions`: the nearest ancestor a live session record names, through `process_table.nearest_named`). Each session found gets `holder_message_text` through `send_holder_message` (`send.py --to <session> --from disk_floor`). natedev gets `floor_out_of_reach_text`, one line per busy target and who was told. Only when no session was told does the phone get a page too (catalog entry `sweep.disk_floor`, sent through `push_texts.user_send_argv` as `send.py --to user --text-id sweep.disk_floor`; `docs/as-built/message-clarity.md`): `page_paths` lists exact paths, busy targets first, then the deepest measured folders outside build caches by size, as many as fit under 500 characters (`PAGE_PATHS` at most), and the action asks the natedev session which paths it may remove.
- **Growth** (free space fell more than `UNEXPLAINED_FALL_BYTES` 10 GiB beyond build-cache growth since a floor sweep at most `GROWTH_WINDOW_SECONDS` 30 min earlier; this sweep's free is read after the scan that measures its caches (`scanned_free`), and the record's free before its caches walk, so a target another process deletes during either walk cannot read as a fall. On 2026-10-25 a free read from before the scan reported a 122.6 GiB fall while 123 GiB was freed. A target held by a build hold counts 0 bytes, so the growth check runs only when the previous record's `held_roots` equals this pass's held set; an older record without it skips the check. The sweeper records its own last delete per target in `target-deletes.json` beside `floor.json`, and a directory mtime no later than that time plus 2 s does not make a target held. On 2026-10-29 its own deletes made a 34.7 GiB target look written during a hold, and a false 36.4 GiB fall was reported) and **large removal** (more than `LARGE_REMOVAL_BYTES` 32 GiB): natedev alone (`send.py --to natedev --from disk_floor`), at most one per `ALERT_INTERVAL_SECONDS` (1 h) counted from the last delivered alert.

`send_floor_alert(message, channels: FloorAlertChannels.NATEDEV | NATEDEV_AND_PHONE)` returns whether either `send.py` call delivered: exit 0 or 1 counts for the natedev message, while only exit 0 counts for the user channel. The texts name what fell, what grew and the largest directories outside the caches, read from `disk.json` as `AvailableDiskMeasurement | UnavailableDiskMeasurement`. `buildlog disk` adds `outside_build_caches` (directories one and two levels under each measured folder holding at least 1 GiB outside cargo target dirs as `sweep.is_cargo_target` decides them, with growth and largest child, so a scratch target is never listed as unexplained growth), `outside_build_cache_totals` and `previous_measured_at`. `send.py`'s `log.jsonl` lines carry `text`.

### Rust release trial

`rust_release.py` keeps a trial ended by a kill (status 128 or more, -9/-15, or signal 9/15 or SIGKILL/SIGTERM in its output) at `waiting` with reason `<step> killed; retry next night`; a genuine failure stays `failed`.

### `verify.sh` example guard

`verify.sh build <pkg> [--bin <name> | --example <name>] [--release] [--features <list>]` builds what a smoke run or live shot launches: `BUILD_TARGETS_PY` reads the package's bins (or the one named bin or example, with its required features), `take_build_args` refuses a package with no binary and a target it lacks (exit 2), and `run cargo build --workspace --bin <name>…` builds under the workspace's feature set with the build hold, the cargo token, memory admission and a call record (verb `build`). `print_built_binaries` then prints `binary: <target_directory>/<debug|release>/[examples/]<name>` for each one. It has no pass record and no Mac offload. A helper's raw `cargo build` had needed the user's approval by hand on 2026-10-23; `/unit:direct` gives helpers this line.

A gate run (`test <pkg>` with no `--filter` and no named target, `--features` allowed) and `final` read `cargo metadata --no-deps --format-version 1` once into `GATE_METADATA` and run `UNTESTED_EXAMPLES_PY` before the cache lookup and any build. An example target is an offender when a source line matches `^\s*#\[(cfg\(test\)|(\w+::)*test)\]`, whatever its `test` setting; a directory example (`examples/<dir>/main.rs`) is scanned through every `.rs` under its directory. An example that sets `test = true` is an offender too. A test offender prints `example <name> holds a test: <file>:<line> has <attribute>, and examples carry no tests.` and `move it into <package>'s src/ or tests/, or delete it.`; a `test = true` offender prints `example <name> sets test = true in <manifest>, and examples carry no tests.` and `remove test = true from its [[example]] entry.`. After all offenders, the call exits 2 with no cargo call besides `metadata`. `read_metadata` reuses `GATE_METADATA`. `verify.sh example-test` exits 2 with `verify.sh: example-test is removed: examples carry no tests (user, 2026-10-04).` before anything else.

### Codex launcher capacity (`scripts/agents/codex_mesh.py`)

Turns end as `TurnCompleted | TurnRefusedForCapacity | TurnFailed`; runs as `RunCompleted | FailedBeforeThread | FailedWithThread | CapacityRetriesExhausted`. Capacity is the error's structured `serverOverloaded` / `flexUnavailable` or the message `Selected model is at capacity`. Capacity resumes the same thread on the same roster entry: waits from `CAPACITY_WAIT_SECS` (30 s) doubling to `CAPACITY_MAX_WAIT_SECS` (300 s) within `CAPACITY_BUDGET_SECS` (1200 s), one worker-log line per wait, and a resume turn saying the last turn stopped for capacity with its edits in the tree. The budget is per busy spell: any turn that ends without a capacity refusal resets it, and an owed resume after such a turn starts at once. Roster status `waiting_capacity` holds the thread id and `launcher_pid`; once a spell's budget runs out it is `capacity_exhausted` and `start` exits 1 with `codex_mesh: <worker>: model still at capacity after <N> retries over <M> min; thread <id> stays on the roster (codex_mesh.py end --to <worker>)`. `send` to `waiting_capacity` stores the message in `<worker>.pending.json` under an flock for the resume turn; `send` to `capacity_exhausted` exits 2; to a finished (`done`/`failed`) worker it exits 1 with `codex_mesh: <worker> is <status>, not running; read its summary file`. The fast-failure retry on a new app-server runs only for `FailedBeforeThread`. Liveness comes from `thread/read`, typed `ThreadLive(turn_id) | ThreadActiveWithoutTurn | ThreadIdle | ThreadStateUnknown(reason)`: `idle`, `notLoaded` and `systemError` (the status the app-server leaves after any failed turn, a capacity refusal included) read `ThreadIdle`, and a status the protocol does not define reads `ThreadStateUnknown`. A relaunch replaces an entry only on `ThreadIdle`, except a `failed` entry, which relaunches after `_end_unwatched_turn(port, thread_id, log_path) -> RelaunchAllowed | RelaunchBlockedByLiveTurn` repeats the dead launcher's cleanup (blocked: exit 2, `thread <id> still has a live turn that could not be interrupted; relaunch once it ends`), and a `waiting_capacity` entry whose launcher is dead, which relaunches without a read. `agent-registry.md` (Addressable codex workers) has the full mechanism.

## Invariants

- Every compiling step and every BRP launch passes the memory gate before it starts. Sweep, `cargo fmt` and `taplo` steps never wait on it, so the disk floor is never held by memory.
- Admission and hold check errors stop the step. Only an explicit admission answer allows it to start; a wait limit grants nothing.
- The disk floor never removes output from a target whose cargo locks a build holds, removes no more than the shortfall plus the last group's overshoot, and prints no new line containing `removed` (`scripts/buildlog/parse.py` counts those lines as freed bytes).
- Build steps skip the Python hold check when the holder directory is missing or the shell confirms a readable, searchable, empty directory. A memory wait never starts a build without memory.
- `BUILDLOG_MEM_WAIT_S` and the gate outcome are set in the calling shell before any `| tee` pipe; a step's recorded start excludes the wait.
- The sccache server stays in `builds.slice`; moving only the steps would leave every compile outside the limit.
- Raising a step's oom_score_adj never stops or alters it: a failed write is silent, the `|| true` keeps the scope shell running when a caller exports `SHELLOPTS=errexit`, and exit status and output pass through.
- A memory kill is never recorded or cached as the tree's lint or test failure; it re-runs once and stops at the second.
- A cargo token is reclaimed early only through a `holder_pid` that names a gone process; holder and waiter share one pid namespace. The guard file is never removed.
- Holder files supply current hold state. Old cycles distinguish files still in force from completed holds. A release removes its holder file at once. Historical log rows never decide whether a build can start.
- Releases go by session id, never by name. A session that cannot be messaged is never recorded as a recipient.
- Hold changes use `release.lock`. Release delivery uses the ended cycle after the holder file is gone. A damaged record is set aside by a changing command, never by `status` or the dailies.
- `steps.mem_wait_s` is the memory wait and `steps.wait_s` the call's lookup and token wait; any column change bumps `SCHEMA_VERSION`.
- Only `ran` CI jobs carry duration and queue time. CI days key on the run attempt's `started_at` everywhere.
- The window report is host-scoped; the daily report aggregates hosts. A run's own peak comes from `ci_anon_bytes` / `builds_anon_bytes` samples, never from `memory.peak`.
- Only the floor-out-of-reach alert reaches the phone; diagnostics go to natedev.
- Tests never read the real cgroup tree, `/proc/meminfo`, `/proc/pressure/memory`, journal or transcripts, and never write `~/.local/state/buildlog`, `build-hold`, `build-hold-release`, `notify` or the agent notes: they take `BUILDLOG_MEMINFO` and `BUILDLOG_MEMORY_PRESSURE` from `scripts/lint/memory_test_support.py`, set `BUILDLOG_*_CGROUP`, `BUILDLOG_TRANSCRIPTS`, `BUILD_HOLD_DIR`, `BUILD_HOLD_RELEASE_DIR`, `HOME`, and stub `journalctl`, `zramctl`, cargo and git on `PATH`. Tests set the hold variables for a checkout's scripts; installed scripts refuse to run with them set.
- When `BUILDLOG_LIVE_MEMORY_TRIPWIRE` names a record file, the shell gate and Python checker refuse a path that resolves to `/proc/meminfo` or `/proc/pressure/memory` before reading it, append a JSON record, and name the fake readings the test must set. The merge gate sets this variable for every test module and fails any module with a recorded live reading. Two limits apply: `test_memory_admit.py::test_default_pressure_still_returns_pressure_when_tripwire_is_unset_or_empty` removes the tripwire and reads live pressure by design; a failed record write still refuses the reading but leaves no record, so the gate detects only recorded readings.
- A verify.sh routing test follows `scripts/direct/test_verify_untested_examples.py`: cargo passes `metadata` to real cargo and logs every other call, git is stubbed, and the environment drops `UNIT_RUN_DIR`/`UNIT_TEAM_ROLE` and sets `BUILDLOG_OFF=1`, `BUILDLOG_SCOPE=0`, `BUILDLOG_MEMINFO`, `BUILD_HOLD_DIR` and `CARGO_TARGET_DIR`. Tests set `BUILD_HOLD_DIR` for a checkout's scripts; installed scripts refuse to run with it set.
- Times shown are in the user's zone through `user_zone()`; stored instants are UTC. An `HH:MM` release ETA names the zone in which it was supplied.

## Calibration and gotchas

- **Unfaked memory pressure.** On 2026-10-29, `test_brp_launch_gate.py` took 169 s against a 6 s median because its pressure reading was unfaked.

- **Memory gate sizes.** Alone, a step is admitted at `min(need + reserve, 12 GiB)`, and 12 GiB (steve's slot floor) is also the fallback `need`. The build-log tier is 0.65 x the build-log p90 (measured p90 anon share 61-65%), conservative until 5 measured runs exist per repo and step; a repo with neither tier uses the step's measured p90 over every repo. A build never starts without memory; under a sustained overload it waits, first in line after 15 min. Quiet use outside builds is about 20 GiB of 60.5. The limit message says "15 min" whatever `BUILDLOG_MEM_WAIT_LIMIT_S` holds. Reading `MemAvailable` before the anon reads, or outside the lock, admits on stale numbers.
- **No stagger between release notices.** `memory_admit.check` runs the reservation read, the meminfo read, the decision and the reservation write under one exclusive `flock`. Fresh steps count their full need for 5 s. Later checks use resident plus swap readings and add no promise for future growth. Builds released together cannot count the same free memory.
- **Release outcomes vanish with the last holder file**; set-aside `*.damaged-*` files are never cleaned up. A holder joining a no-cycle hold learns nothing until the final release line tells it to broadcast.
- **earlyoom never logs "killed";** its line is `sending SIGTERM to process <pid> uid ... "<comm>": ...`.
- **zram is invisible to slice limits.** earlyoom counts zram's virtual size as swap; `MemoryMax` counts RAM only, and compressed pages are charged to no slice.
- **`MemoryHigh` on a slice holding a heartbeat** (the runner's `Runner.Listener`) stalls it until GitHub drops the runner; such a slice gets `MemoryMax` only and its services `OOMPolicy=continue`. `MemoryHigh` on `builds.slice` throttled builds not short of memory, since it counts page cache.
- **At its ceiling CI hits `MemoryMax` thousands of times with no kill;** a large `max` delta is reclaim, and its cost shows as stall seconds. `memory.peak` never falls without a reset; CI's reads above 18G from before the limit existed.
- **CI raise threshold.** Raise CI's `MemoryMax` only for an isolated run (one CI attempt alone in `hana-ci.slice`) with an `oom_kill`, or repeated isolated runs with sustained ceiling hits and at least 60 s of slice stall each, after checking minute coverage and build mix. Both runners share the slice, so an overlapping run is no evidence for a per-run raise. A changed limit needs another measured day after it.
- **CI's jobserver.** Inside a runner unit (`PrivateDevices`, `DevicePolicy=closed`) the pool device exists only with `BindPaths` and `DeviceAllow`; with an ACL alone `CARGO_MAKEFLAGS` yields a jobserver warning that hana's release job treats as failure.
- **sccache.** `sccache --start-server` forks and exits, so a service using it dies at start; with `SCCACHE_START_SERVER` in the environment every other sccache command fails, hence `ExecStart` only.
- **A step's own peak and stall exclude its compiles**, which run in `sccache.service`; the slice samples and snapshots see them.
- **sccache's compiles do not inherit a step's 500.** The server starts them in `sccache.service`, not in the step's scope; the unit's `OOMScoreAdjust=500` is what ranks them with the build steps; without it they sit at 200 with the sessions' processes.
- **Launch coverage.** `launches.py` globs one transcript level and misses launches in subagent transcripts (11 of 37 on the measured day). About a third of real launches lack `parameters.path`; `metadata.workspace` is only a folder name. `binary_path` appears for examples too, so only `metadata.launched_as` names an app. Counts are per pass; a launch count comes from stored `brp-launch` steps. Branch and SHA are collection-time facts. Transcript fixtures copy real lines.
- **CI re-runs.** GitHub copies every finished job into the new attempt under a new `job_id` with `created_at` at the re-run and the earlier stamps, which read raw gives a negative queue time and a duplicate duration.
- **Build-folder waits.** The `calls` table also holds port-lint calls, so every query over the call population, counted calls and token holders alike, filters `tool = 'verify.sh'`. Holders are fetched by `ended_at`, not `started_at`, so a holder that began the previous day is found.
- **Mac commands.** Tailscale SSH runs them under `/usr/bin/login`, which exits 0; judge the printed `rc=`. A sync pause never expires (the report's Mac line shows it), an unreadable pause file reads as paused, and `pause` can wait up to 30 s + 2 x 600 s for a running sync. `polled.json` is in `ci/` so sync carries it to the Mac; `sync_paused.json` stays local.
- **Disk.** send.py exit 1 (queued) counts as delivered. `disk.py`'s first walk is the cost (35 s under load 104). A file hard-linked into a target dir and elsewhere counts outside the caches. `floor.json` and `disk.json` hold only the latest record; past sweeps come from `journalctl --user -u disk-floor.service`. `sweep.py` reads `disk.json` by path and never imports `scripts/buildlog`, since `disk.py` imports `sweep`.
- **Disk floor order.** A no-op cargo build writes nothing under `target/`, and relatime refreshes atimes at most once a day, so only the use stamp records a step that compiled nothing. The stamp lags a lint step by up to 5 minutes (`invoke.sh`'s sweep rate limit), which only reorders targets used within the same 5 minutes. The build log's `sweep_freed_bytes` counts each workspace's budget sweep and the floor sweep after it together, so it is not the floor's cost alone; the journal's per-target lines are.
- **procps cuts user names** over 8 characters unless the format says `user:32`.
- **Codex.** On an idle thread the app-server opens a turn per queued message, so never `thread/queue/add` to a thread no launcher streams. `thread/read` can report active with no turn id; get the id from a steer probe before `turn/interrupt`. `turn/interrupt` errors when the turn ended in between; only a re-read tells that from a live turn.
- **Dailies.** The run-out time rounds to the minute in epoch seconds (rounding aware local time loses the DST fold). `resets` is the writing machine's wall time with its offset (2026-10-12: notes travel between machines in hanadocs, and an offset-free value read on the other machine was off by the zones' difference); `note_file.reset_time` reads it for `agent_notes.still_ahead`, `quota_alert.ahead` and its two account checks, and `codex_pacer.parse_local`, taking a value written before the offset as the reading machine's wall time. A naive `limit_reset` is the writing machine's wall time. Every subprocess dailies test sets `HOME` to a temporary directory.
- **`verify.sh` guard.** A failing `cargo metadata` exits with cargo's status under `set -e`, not 2.
- **Live scripts.** Units run `~/.claude/scripts/direct/board.sh` and `verify.sh` while they change, and bash reads a script as it runs: replace either by writing a temp file beside it, setting its mode, and `mv`ing it over.
- **A target with neither marker.** A folder made before a build that runs with `CARGO_CACHE_RUSTC_INFO=0` has no `.rustc_info.json` and no `CACHEDIR.TAG`; the floor and the disk measurement do not see it. Nothing on natedev sets that variable.
- **Cargo's tag is not only on targets.** `~/.cargo/registry` and `~/.cargo/git` carry the same `CACHEDIR.TAG` text, and other tools write the file with their own text; the tag counts only with cargo's line and a build tree beside it.
- **basedpyright** exits 3 in every checkout (`pyrightconfig.json` names an absent `.venv`); 0 errors and 0 warnings in its output is the gate.

## Why

- **Admission by free memory, not by slice limit.** `memory.high` counts page cache and throttled builds that were not short of memory; `MemAvailable` is what earlyoom acts on. 12 GiB matches the floor steve already uses for slots, and a step's expected need replaces it once history exists, so parallel large builds no longer start together into memory only one of them fits in.
- **Target first below the disk floor.** Ordering every idle build unit by compile age spread each shortfall across the targets in active use, which rebuilt the output minutes later. One worktree's target is what a unit owns, so the least recently used target goes first and a target used minutes ago goes last. A forecast mode was ruled out: every build goes ahead, and the journal names whose cache went.
- **Scratch first below the disk floor.** A scratch target belongs to no worktree and is rebuilt only if its session is still working, so it goes before output a unit will need again. On 2026-10-08 a 140 GiB scratch target outlived managed targets idle for hours because it was used more recently, and a scratch target in its first build reached 22 GiB unseen, listed by the alert as growth outside build caches. No floor hook runs inside scratch builds: the 2-minute timer covers them, at about 2 GiB a minute against 300 GiB of headroom. A structural target rule (a child folder holding `.fingerprint` and a cargo lock) was rejected: one listing per walked folder for the no-marker case nothing here produces. Orphaned files still go first from every idle target, because losing one costs nobody a rebuild.
- **One slice for every session build, sccache included.** Every compile reaches the sccache server, so the server's cgroup is where compiles are charged; a limit on the step scopes alone would bound nothing.
- **CI in its own pool, a smaller slice and a lower kill order.** Shared steve slots alone did not stop kills (a CI run lost both Linux jobs after it). Its own 14-slot pool keeps CI from starving sessions and the reverse; `PIPELINE_JOB_OOMSCOREADJ` is the only setting that reaches job processes, because the runner sets every job to 500 itself. At 100 a CI job goes after a build step (500) or a session process (200) of the same size.
- **Build steps at 500, and no `--prefer`.** The level sets the order and size decides within it. A `--prefer` for compiler names (+300) let two hung hana tests (11.4 GB, 15.5 GB) outlive 26 smaller processes, six CI compilers among them; without it, a hung 15 GB test scores about 1100 against a 2 GB CI compiler's 750, and a session's rust-analyzer at 200 stays behind every build step of similar size. The adj is set inside the step's scope, so every process the step starts inherits it.
- **Every session at once, through reserving gates.** The 11:12 PDT episode on 2026-10-04 (21 kills) came from a release into a gate that read memory before compilers grew. New steps now keep a short start promise, then use measured memory. Every build starts through the memory gate after a release.
- **A damaged record releases everyone, not no one.** Setting it aside and falling back to a broadcast cannot strand held sessions; each still passes its own memory gate.
- **Broadcast by id.** Names can belong to two sessions, and `top_level.py` once deduped them, so one of two same-named sessions never heard the hold.
- **A memory kill re-runs once.** The kill says nothing about the tree; a second kill stops the call so a starved machine does not loop.
- **zram over zswap.** A cache in front of a full swapfile adds no capacity; zram adds compressed space that does not depend on the swapfile.
- **Every average gets a p95.** An average hides the long runs that make waits; nearest rank needs no interpolation and matches the old p75 index for every n.
- **Two build-folder rows.** A worker's own verify.sh calls run one at a time, so its wait behind its own call costs nothing; only the wait behind another worker of the same worker session is delay.
- **Ruled out** (do not re-propose without new evidence):
  - systemd-oomd for builds: it kills a whole cgroup, and every session's compiles share one.
  - Admission by each crate's measured peak, or a per-crate gate: no source records the peak, and no isolated run met the threshold.
  - A nextest thread cap or a per-run memory cap in `verify.sh`: no isolated run met the threshold, and the widget drawn-pixel test group already bounds the largest step.
  - A `MemoryHigh` gate or `MemoryHigh` on either slice (see gotchas).
  - A `CARGO_BUILD_JOBS` fallback on the runners: the pool's jobserver reaches CI jobs.
  - A `steve-clients` group: the ACL already grants the runner users, and group membership is fixed at login.
  - Catching `AttributeError` instead of validating the cycle shape: it would hide code defects too. `release --resume` releasing the sole holder of any no-cycle hold: it could end a hold nobody had begun releasing.
  - A 10-minute snapshot search: an edge snapshot more than 2 minutes off misplaces the window. A per-call kill count alone: it cannot tell two single kills from one step killed twice.
  - Keying `ci_section` by job `created_at`: drops post-midnight jobs of a run started before midnight.
  - Counting build-folder wait that no same-session holder covers as the call's own: it would hide waits with no recorded holder.
  - A hook on `brp_launch` to record launches, or recording from inside bevy_brp_mcp: the collector reads transcripts instead. Appending launches to the host's monthly file: the per-launch file makes the record id the dedupe.
  - Keying the example guard on the target's `test` setting or advising `test = true`: examples carry no tests (user, 2026-10-04).
  - Withholding the phone push when a removal failed, or cutting a path's last component to fit 1,024 characters.
  - Queuing a message to an out-of-retries Codex thread (it opens a turn nothing streams); changing the service tier on capacity.
  - The dailies renderer importing the note code from `scripts/whoami`: it parses the flat frontmatter itself and imports only `run_out`.

## Not built

`verify.sh ... --target-dir <name>` (a per-helper build folder with its own cargo token, pass records shared across folders, `calls.target_dir`, schema 10) is parked. It returns when the report's `Build-folder turn, behind another worker` row shows real time queueing for a worktree's build slot.

A second promise rule is measured and declined (showrunner, 2026-10-28: simple wins). The rule: a running build whose need is above a limit keeps its full promise; the running builds at or under it are promised the largest gap in full plus `max(0, 0.6 x need - anon)` each. The replay used 4 h of 5 s admission samples (2026-10-28 03:27-07:27Z, 240 waits, 1863 wait minutes), and "short" counts admitting ticks where the running builds' real growth after the tick passes `MemAvailable` minus the reserve. With a 6 GiB limit the rule saves 331 of 1863 minutes against 249 for the current rule, with the short rate at 0.8% against 0% (5 GiB: 326 min, 0.9%; 8 GiB: 501 min, 1.4%). The same rule limited by the waiting step's need never gets below 6.9% short. At about 4% of the wait for a second rule and a nonzero short rate, it is not built; a shortfall is the 2026-09-30 freeze. Do not measure it again unless the mix of steps changes.
