# Unit tooling: function-length hook, showrunner footers, stall watcher and launcher follow-ups

## What it is

A set of agent-session tools in `~/.claude`, all Python (standard library) or zsh/bash, with tests beside the scripts:

- A PostToolUse hook that blocks an editing agent the moment an edit leaves a Rust function over clippy's `too_many_lines` limit.

- A Stop hook that makes every showrunner reply end with the current footer and a `Waiting on:` block, with a per-production off switch (`/showrunner:footer`) and an adhoc-review pause.

- Cargo-token hygiene: each verify step runs in its own process group that a release or reclaim stops.

- Launcher changes: `implement.sh --to <worker>` carries follow-up work to a worker still open (`review.sh --to <worker>` does the same for reviews; see `long-lived-workers.md`), a Claude worker starts at its registry effort, a pane-derived summary is plain text, and `/unit:report on|off` switches a unit's progress updates.

The 96-hour measure ran from 2026-10-07 01:44:05 EDT to 2026-10-11 01:44:05 EDT. It found 27 `too_many_lines` failed steps among 763 hana clippy steps. The rate was 3.539 per 100 against a ≤3.3 limit: **FAIL** (baseline 13.3). Sole-cause cost was 0.116 worker-hours per day against ≤0.27: **PASS** (baseline 1.07). All four Claude/Codex controls on natedev/Mac passed.

The [multiply-add hook and lint rewrite](build-followups-mul-add.md) and the [one-command unit start and checkpoint merge](showrunner-automation.md) have their own docs.

### Function-length hook

Files: `scripts/hooks/fn_length_lib.py` (checker), `scripts/hooks/post-tool-use-fn-length.py` (entry), `scripts/hooks/test_fn_length.py`. `settings.json` registers `"$HOME/.claude/scripts/lib/py" "$HOME/.claude/scripts/hooks/post-tool-use-fn-length.py"` in the `Edit|MultiEdit|Write` PostToolUse group, after basedpyright and before the mul-add hook. `codex_hooks.py` installs and trusts the same command for Codex `apply_patch`, alongside mul_add and the berth `PreToolUse` check (`pre-tool-use-berth.py`, timeout 30); every handler must be trusted and enabled.

- **Payloads.** One entry serves both agents. `applied_rust_edits(raw) -> AppliedRustEdits | IgnoredEdit` returns `agent`, `tool`, `cwd`, `files` and `replacements`. Claude `Edit`/`MultiEdit`/`Write` with a `.rs` `tool_input.file_path` gives `agent="claude"`. Codex `apply_patch` (`tool_input.command` is the patch text) gives `agent="codex"` and the `.rs` files named by `*** Add File:`, `*** Update File:` and `*** Move to:` headers. Deletes are ignored. Each file has a tuple of `Replacement` pairs with the applied old and new text. The multiply-add hook uses these pairs to select written lines. The function-length hook checks the whole file. The entry returns before any import when the raw text holds neither `.rs` nor `\u`.
- **Check.** `long_functions(rs_file: os.PathLike[str] | str) -> tuple[TooManyLinesLintScope, list[FunctionLength]]` returns the non-exempt functions over the threshold, in source order; empty when the scope is disabled or the file is unreadable or not UTF-8. `TooManyLinesLintScope(enabled, threshold)` and `FunctionLength(name, line, lines, exempt)` are plain `__slots__` classes. The whole file is checked, not only the touched lines.
- **Verdict.** One JSON object: `decision: "block"`, `reason`, `continue: true`, `systemMessage: "fn-length: <summary>"`, and `hookSpecificOutput.additionalContext`. The reason is `fn <name> at <path>:<line> is <N> lines (limit <T>)` joined by `; `, then `: split it now. The edit was applied.`; `<path>` is relative to `realpath(cwd)` when inside it, else absolute. It never names the exemption attributes.
- **Log.** Every block appends one record per affected file to `blocks.jsonl` under `FN_LENGTH_HOOK_STATE` when set, else `~/.local/state/fn-length-hook` (directory mode 0700): `{"at", "agent", "tool", "cwd", "file", "threshold", "functions": [{"name","line","lines"}]}`. Both agents log, so a re-measure can prove both fired.
- **Lint scope.** `read_clippy_lint(rs_file, lint, group) -> ConfiguredClippyLint(level, package_dir) | UnavailableClippyLint` (`NO_PACKAGE`, `UNREADABLE`) walks up to the nearest `Cargo.toml` whose text names `package`; no `lints` text means `UNSET`. `lints.workspace = true` follows `package.workspace` or the ancestors to `[workspace.lints.clippy]`. The level is the `too_many_lines` entry, else `pedantic`, as a string or a `{level = …}` table. The hook fires at warn, deny or forbid. The threshold is `too-many-lines-threshold` from the nearest `clippy.toml` or `.clippy.toml` walking up from the package directory, else 100; a non-integer or negative value disables the hook. `read_clippy_lint` is shared with `mul_add_lib.py`, so its changes affect both hooks. `fn_length_lib.py` also exports `target_may_be_no_std` for multiply-add; the function-length checker does not use that root exemption.
- **Counting.** `count_body_lines(body)` is clippy's loop: strip the body, split on newlines, and count a line only when code appears outside a comment, carrying block-comment state across lines (`/*` before `//` enters a comment, `*/` leaves it). Strings are not parsed, so `"a // b"` counts when code precedes it. A line of `code /* c */` counts; the signature, attributes and doc comments never do. Threshold 100 means 101 lines fail.
- **Scan.** `measure_functions(source, *, skip_example_tests=False) -> list[FunctionLength]` tokenizes with one regex (`_TOKENS`: line and nested block comments, strings, raw strings, char literals, `#[`/`#![`, delimiters, `!`, and the keywords `fn impl trait mod`), pairs delimiters, and walks tokens once. `body_opener` skips parenthesized and bracketed runs and gives up at `;` or `}` (no body). Names come from `_function_name` (raw identifiers `r#x`, comments between `fn` and the name). Closure lines count in the enclosing body; a nested `fn` is also measured on its own. Macro bodies (`macro_rules!`, `name! { … }`) are skipped via `macro_before`; a keyword is never a macro name and `!=` is never a marker.
- **Exemption.** `_is_exempt` accepts `allow(…)`, `expect(…)` or `cfg_attr(…, allow|expect(…))` naming `clippy::too_many_lines` or `clippy::pedantic`. Outer attributes pending since the last `;`, `{` or `}` attach to the next item: a `fn` is exempt, and everything inside an `impl`, `trait`, `mod` or `fn` block is exempt. `#![…]` exempts the rest of its block. A keyword inside a signature (`-> impl Fn()`) is not an item. With `skip_example_tests`, `#[cfg(test)] mod` blocks in a package-root `examples/` target are skipped.

### Showrunner footer, Stop hook and switch

Files: `scripts/production/dailies_render.py`, `scripts/hooks/stop-showrunner-footer.py`, `scripts/hooks/showrunner_footer.py`, `commands/showrunner/footer.md`, the Footer section of `commands/showrunner/produce.md`, `commands/showrunner/dailies.md`. The footer hook is the last entry of `settings.json`'s Stop group, after `stop-assistant-prose-banned-words.py`; `stop-conversation-pause.py` is earlier, straight after `stop-delegate-continue.py`.

- **Footer renderer.** `dailies_render.py --footer --zone <IANA zone> [--next-run <HH:MM[+N]>] [--nothing-needed] [--at <YYYY-MM-DDTHH:MM[±HH:MM]>] [--outstanding <outstanding.json>] [--doc <production doc>]` prints `footer()`, the same text a dailies report ends with: an empty line, `---`, `HH:MM <zone> update:`, the counts line when anything is counted, an empty line, then `* ` bullets: `build hold: <name> holds builds since HH:MM <ZONE> for <purpose>; expected to release …` lines (a session to act on during a release nested as `  * `), each Agents line in the dailies report's words (no `### Agents` heading), and last `* next dailies: [Day ]HH:MM <zone>` or `* no dailies scheduled`. ` - nothing needed` is appended only when `--nothing-needed` is set and no outstanding item is visible (a deferred item shows only after its `after` time). `--next-run HH:MM+N` means N days later; `--at` names one occurrence of a repeated hour. Bad input prints `dailies_render: <error>` and exits 2.
- **Counts line (2026-10-16, showrunner's footer-counts plan).** `scripts/production/footer_counts.py` reads each count when the footer renders and stores none: `changes` is `len(change_review.pending(list))` for the list `change_review.list_path(doc)` names, `proposals` is `len(issues.open_issues(folder, "proposal"))` for `proposals_table.issues_folder(doc)` (that module is imported only for a doc with a Proposals line), and `projects`, for a doc with `- **Improvement queue:** <ledger>`, counts ledger lines `- <date> <title> (<file>) — <status>` whose status starts with `proposed`, or with `accepted` and holds none of `assigned`, `applied`, `built`, `declined`. A source that cannot be read counts 0. `counts_line` writes `For you: 2 changes to review, 1 proposal, 3 projects, 1 question`, zero counts left out, None when all are zero. The hook's `render_footer` passes `--doc`; `dailies_input.py` writes the input's `doc`, which `render()` reads; `update_registration.py footer` passes the doc to `footer_main`. Questions stay out of a footer's line, since the Waiting on sentence carries them. The status line's counts row adds the open questions (`showrunner_footer.counts_line`, questions from `open_questions`). With footers off, `update_registration.py footer` prints no counts line, and `footer_block_reason` hands an all-off reply to `counts_block_reason(reply)`, which blocks a reply with any line that starts with `For you: ` (user, 2026-10-18: the user reads the counts in the status line).
- **Waiting on block.** The showrunner, not the renderer, writes it after the footer: two empty lines, `Waiting on:`, an empty line, then `* ` bullets: the open-questions count while any item waits on the user, then ETA items soonest first, then no-ETA items. The text of a user item never appears there.
- **Stop hook entry.** `stop-showrunner-footer.py` imports only `json`, `os`, `sys` and `typing` until it knows the session is a showrunner. It reads `StopPayload` (`session_id`, `transcript_path`, `last_assistant_message`, `stop_hook_active`, `agent_id`) and passes when `agent_id` is present or the session id or reply is empty. `stop_hook_active` skips only the footer check (`skip_footer`), not the question check or the turn rule. **Turn rule (2026-10-16, showrunner's rule for turns the user did not start; its block retired 2026-10-18).** `turn_input.read_turn(transcript_path)` reads the transcript backwards in 1 MiB chunks (64 MiB at most, else unknown) to the turn's opening prompt entries: every `user` entry with an `origin`, or a typed one with none, and every `queued_command` attachment (an older one without an origin is read from `commandMode` or its `<cross-session-message` tag). `TurnInput.machine_only` holds when every kind is `peer` (the update tick arrives through `send.py`, so it is one) or `task-notification`; `denied` is true when an error tool result in the turn carries `denied by the Claude Code auto mode classifier`, and nothing reads it now. On a machine-only turn, after the reviewed-question check, `block_reason` passes exactly `-` without the footer and sends any other reply on to the footer check. The block that answered every other reply with `nothing needs the user: reply with -` is retired (user, 2026-10-18: it blocked the reply that showed a `/showrunner:retire_unit` result). An unreadable transcript leaves the rule out. A session is a showrunner when a `showrunner-*` notifier instance's `conf` (under `NOTIFIER_STATE_DIR` or `~/.local/state/notifier`) holds `TARGET=session:<id>`. It collects each production's `FooterState` and prints `{"decision": "block", "reason": …}` from `block_reason`. Any exception prints `stop-showrunner-footer: <type>: <message>` to stderr and exits 0.
- **Production.** `read_production(instance_dir) -> Production | None` takes the doc from the last token of the instance's `CHECK`, requires `Status: PRODUCTION — running`, takes the zone from the user's zone setting (`scripts/lib/user_zone.py`; the doc's `- **User zone:**` line is not read), and builds `schedule` from state: `ScheduledDailies(next_due)` when `ENABLED=1`, else `NoDailiesSchedule.PAUSED_OR_UNSCHEDULED`. Anything unreadable gives `None` (the production is skipped).
- **Check.** `block_reason(instance_dirs: list[str], reply: str, states: dict[str, FooterState], *, skip_footer=False) -> str | None` first runs `check_reviewed_text`, before the footers-off return and the `stop_hook_active` skip: a reply missing a pending reviewed question, or asking the user anything unregistered, is blocked (`docs/as-built/message-clarity.md`, Question review in showrunner replies). A pending item leaves the file once a reply carries it, even a reply blocked for something else. Then `footer_block_reason` runs:
  1. No running production, or every production's state `OFF`: pass with no check at all.
  2. When the reply ends in a valid Waiting on block (`waiting_bullets`), `waiting_format_error` runs for each production. ETA bullets lead with `[<Day> ]HH:MM[+1][ (HH:MM[+1]–HH:MM[+1])] - `; no-ETA bullets lead with `no ETA measured - `; a bullet with neither lead must be the open-questions count line. It blocks on an ETA mid-line, a zone after a leading time (all-caps word of two to five letters), ETA items out of (day, minutes) order (unmarked is today, `+1` tomorrow, a weekday the next such day in the production's zone, today's own weekday being today), and kinds out of order (count, ETA, no-ETA). The reason names the rule and shows `19:45 (18:20–23:55) - startup Phase 16` and `no ETA measured - <item>`.
  3. `open_questions(productions) -> int | None` counts the items now due in every production's needs-user file: an item with no `after`, or whose `after` is at or before now in the production's zone. It is `None` when a file cannot be read, and the check is then skipped. `open_questions_error(bullets, expected) -> str | None` requires exactly one count line, `count_sentence(n)`, as the first bullet when n is above 0 and none when n is 0. Any other bullet without an ETA or `no ETA measured - ` lead is refused. The reason states the ask-once rule and the line to write.
  4. For each production still on, the expected footer comes from `render_footer`, which runs `dailies_render.py --footer --zone <zone> --outstanding ~/.local/state/showrunner/outstanding/<slug>.json` (`--next-run` from state `NEXT_DUE` when scheduled; `--nothing-needed` and `--at` from the reply's stamp) with a 10 s timeout; a non-zero exit or timeout raises `FooterError`. The footer lines must appear in the reply's pre-Waiting part; several productions each take an unoccupied match, and a section stamped differently is re-rendered at its own stamp.
  5. Otherwise the reason is `REASON_HEAD`, the current footer rendered with no `--at`, and a `Waiting on:` example whose first bullet is the count line when any item is due.
- **Stamp.** `stamp(lines, now) -> tuple[datetime | None, bool]` reads the last `HH:MM <zone> update:` line; it counts only when at most `STAMP_WINDOW` (5 minutes) old and its zone abbreviation matches the candidate occurrence (both `fold`s are tried, so a footer in the repeated fall-back hour matches). The bool is whether the last footer bullet ends ` - nothing needed`.
- **Switch.** `~/.local/state/showrunner/footers-off/<slug>` (present = off; `SHOWRUNNER_STATE_DIR` replaces `~/.local/state/showrunner`), keyed like `outstanding/<slug>.json`, so it outlives compaction, `claude --resume` and a new instance target. `FooterState` is an enum (`ON`, `OFF`). `/showrunner:footer [on|off]` runs `"$HOME/.claude/scripts/lib/py" "$HOME/.claude/scripts/hooks/showrunner_footer.py" on|off|status`, which acts on every `showrunner-*` instance targeting `$CLAUDE_CODE_SESSION_ID`; `status` prints `<slug> footers on|off` per production; `on` and `off` exit 0 when already so; with no such instance it exits 1 with `no production targets this session`. Off pauses the footer and the Waiting on block together.

### Production status: run-out and pane lookup

- `scripts/whoami/run_out.py`: `Reading(at, used_percent)`, `read_readings`, and `weighted_rate(readings, end) -> float | None`: percent used per second by `end`, each rise between consecutive readings weighted by 0.5^(age / `HALF_LIFE`, 12 h). A drop (a weekly refill or a redeemed reset), time at 100% and a gap over `MAX_GAP` (15 min: the account sat logged out) are skipped, so rises before a refill still count. None until the counted time, weighted, reaches `MIN_SPAN` (1 h).

- `dailies_render.agent_line` extends `weighted_rate` at the latest reading to 100%, rounded to the minute. When it is None, the fallback divides used percent by the time since the later of the weekly refill and now minus `run_out.WINDOW` (24 h).

- Agents line forms (then the unchanged resets part, `N reset(s) available until <Mon D>` / `no resets available` / `resets unknown`): `claude1: 25%; runs out about Tue 22:02 PDT, before its Sun 23:00 refill; …` (`22:02 PDT today` when today); `…; runs out about Mon 04:00 PDT, so it hits its Sun 23:00 refill first; …`; `…: 1%; does not run out at this pace, so it hits its Sun 23:00 refill first; …` (rate at or below 0); `…: 100%; ran out, back at its Sun 23:00 refill; …`. Unknown usage reads `week's usage unknown; refills …`.

- `agent_section(now, zone, *, at=None)`: with `--at`, when a note's `weekly_usage_checked_at` is later than the stamped minute, each line uses the account's latest reading before the end of that minute (computed in absolute time), and only readings up to it feed the pace; with none the note stands. Notes are the accounts in use (`role` or `sessions`) in `~/rust/hanadocs/agents/*.md`, read by their stable account labels; readings live in `~/.local/state/agent-notes/readings.jsonl`.

### Showrunner settings and stall watcher

- `config/showrunners.json` (git-ignored; `SHOWRUNNERS_CONFIG` redirects it) holds five settings: `threshold_percent` 2, `repeat_minutes` 30, `stall_minutes` 5, `faults_to` `natedev` and `always` `["natedev"]`. `quota_alert.py` sends to `always`, then to each running showrunner by its name now, each name once.

- `scripts/production/stall_watch.py` runs each minute as the run-only notifier instance `stall-watch`. Per tick, under a non-blocking `flock` on `~/.local/state/stall-watch/lock` (a held lock exits 0 at once): for each running showrunner (`registered_showrunners()` with a `socket`), for each unit that `unit_lookup.marked_units(<slug>)` finds with a `LiveClaude`, take its pane and that Claude's pid, session id and socket, and track a stretch. A showrunner that is not running has no one to report to, so its units are not watched.

- The review unit is never watched (2026-10-12): `add_unit.is_review_unit(unit, lines)` is true for `review-unit` in a doc with a `- **Review pool:**` line, the same test `add_unit.py` uses to open it with `/review:direct`. It waits for a `review merge:` line by design, so the watch drops its idle stretch and sends no bump and no tell. A review stuck mid-review still holds its showrunner's merge, which the showrunner sees.
  - A stretch is `Stretch(pane_hash, since, bump_sent, tell_sent, reported_status)` in `~/.local/state/stall-watch/<sha256(production slug NUL unit id)>.json`. The hash covers `session_pane.read_place(place, 400, joined=True)` on the unit's herdr pane. A changed pane resets it unless something was sent; transcript activity (the session's `.jsonl` and its `subagents/` files) moves `since` forward before a report is sent.
  - A unit whose last turn-end line (`holding|gate|decision|blocked|done:`) is `done:`, `blocked:`, `gate:` or `decision:` is waiting, not stalled: no bump, no report, a fresh stretch; `holding:` stays a stall candidate. A unit whose run state (`unit_lookup.run_state` of its Worktree cell) is `run-finished` or `standing-by`, and a unit whose Units row is retired, is skipped and its stretch file deleted. The stall watch does not use `run done` text in the Plan cell. A shell or launcher descendant of Claude (`zsh bash sh implement.sh review.sh verify.sh`, defunct ones skipped) means work is running and resets the stretch, as does any process carrying the unit's marks other than the Claude, its pane and the helpers it starts itself; that mark's slug is resolved through `showrunners.canonical_slug`, so detached work started before a production rename still counts. After a report the stretch holds until work runs or the turn-end line changes.
  - Idle for `stall_minutes` with no work: one bump to the unit's own socket (`stall-watch: you have been idle since HH:MM <zone> with nothing running. Continue your run; …`, key `stall-watch:<unit>:<since>:bump`) and one report to its showrunner (`<unit> idle since …, nothing running; bumped. Last status: <line>`, key `…:tell`) per idle stretch.
  - `send_all` starts every `send.py --to uds:<socket> --from stall-watch --key <key> --text …` together and waits at most 90 s for the batch; a failed recipient is retried next tick with the same key; the stretch flag is set only after a successful send.

- `notifier.sh new <instance> --every <min> --run <cmd> [--timeout <s>]` makes a run-only instance (`RUN=` in `conf`; not combinable with `--to`, `--from`, `--check`, `--command`, `--prompt-file`, `--hold` or `--aligned`; timeout defaults to 120 s). `cmd_tick` starts each due `RUN=` job outside the tick through `launch_run`: a transient `systemd-run --user --collect --quiet --no-block --unit session-notifier-<name>-<pid>-<random>` on Linux; on macOS a `launchctl submit` job that runs `run-due-and-remove <name> <label>` and removes its own label; with neither launcher it logs `run launcher unavailable: <name>; waiting after tick` to `notifier.log` and runs the job after the tick lock is released. The job claims its slot, runs the command with output to `<instance>/run.log` (replaced each run), has a `zselect` watchdog that sends TERM at the timeout, and appends `run timeout` or `run exit <rc>` to `fire.log`. Non-run jobs still run inside the tick.

### Adhoc review pause

`scripts/production/review_pause.py pause | status | resume both|dailies|footers|none` acts on each production targeting `$CLAUDE_CODE_SESSION_ID`. The record is `~/.local/state/showrunner/review-paused/<slug>.json`, `ReviewPauseRecord{dailies, footers}` with each action an `ActionState`: `untouched`, `attempted`, `done` or `skipped` (legacy booleans read as `done`/`skipped`), written atomically before and after each action. `pause` stops dailies (`notifier.sh stop showrunner-<slug>`, 10 s timeout) when enabled and sets the footer switch when footers are on; `reconcile_attempted(instance, slug, path, record)` (shared by `pause`, `status`, `resume`) turns an `attempted` action into `done` when its effect is observable. A failed stop leaves `attempted`, so a re-run redoes only what did not happen. `resume` undoes only `done` actions the answer selects, then deletes the record. `/adhoc_review` Step 2 runs `pause`; Step 5 runs `status` and, if a record exists, asks `Turn dailies and footers back on? (yes / dailies only / footers only / leave off)`, then `resume` (`yes` is `both`, `leave off` is `none`).

### Cargo token and step groups

- `verify.sh` takes the token with `board.sh acquire <dir> <slot> cargo --pid $$ --hold 3600 --wait 1800`; a failed acquire exits 1 (`waited for the cargo token and did not get it`). Each cargo step runs under `STEP_OWNER_PY`: the parent forwards INT/TERM/HUP to the child's group; the child calls `os.setsid()`, and under `cargo.guard` writes `{"group", "start"}` (pid and `/proc` start-time identity) to `locks/cargo.d/owned` only if `holder_pid` still equals the verify pid (a missing `holder_pid` counts as not equal; else exit 125 with `this run lost the cargo token before its step started; run it again.`), then runs the command.
- `board.sh cleanup_owned_group` runs on `release` and on dead-holder reclaim: it checks the recorded leader's identity, `SIGKILL`s the group, waits 2 s, and fails closed (`board.sh: step group still has running processes`, `… leader identity changed`, `cannot inspect step process group`) with the token left in place. An expired lock whose holder is alive is reclaimed without touching its build; the reclaimed holder is appended to `reclaimed_holders`.
- `board.sh release <session_dir> <agent> <resource> --pid <pid>` refuses a pid that is not the recorded holder's: exit 3 when the caller is in `reclaimed_holders` (the new holder owns the token), else exit 1, reason on stderr. Without `--pid`, a token whose `holder_pid` is still alive is refused with exit 1 (`<agent> gave no pid and <resource> is held by live pid <pid>`): the launchers' closing `release` names only the role, which two phases of one session share, so it frees only a gone holder's token. `verify.sh`'s `release_token` always passes `--pid $$`; 0 and 3 count as released, any other status turns a passing run into exit 1.

### Launcher follow-up path

`implement.sh --to <worker> <session_dir> [working_dir] [prompt_file] …` (`--to` first, then the usual positional arguments; the prompt file is the message).

- It skips `worker_name.sh` and addresses the full worker name from `mesh_roster.json` (Codex) or the `workers` ledger (Claude). Before any record it exits 2 with a message when the worker has no matching durable identity (`impl_worker_<slot>.json`: name, slot, family, model, full Claude session id or Codex thread id), is `mesh=none`, is claimed by a live launcher, reads `implementing` while its roster launcher is alive, or is busy (roster not followable, or `claude agents --json` status other than `idle`, or gone).
- It then runs the new-worker path: truncate `impl_summary_<slot>.txt`, write `impl_status_<slot>` (`implementing`, then `implemented` or `error`), `start-pass`, a register line (`follow-up to <worker>`), the follow-up, `finish-pass`, `findings.py landed` (or `abandon --edits-landed` on a worker error) under `PLAN_DELEGATE_RESOLVES_ROUND=1`, and the `launcher:` `done` or `blocked` board post. A trailer appended to a copy of the prompt (`impl_follow_message_<slot>.<pid>.txt`) tells the worker to write the summary last, then post `done`. `implemented` is written only after `finish-pass` and `landed` succeed; a failed write posts `blocked`, writes `error` and exits 1. The launcher's exit wakes the unit director as a new worker's does. A trap releases the claim at exit.
- One claim per worker (`impl_claim_<slot>.json`, `{pid, worker, turn_id}`, under `impl_worker_claim.lock`). A claim whose launcher is dead is dropped and its status set to `error`; an `implementing` status with no claim file and no live roster launcher gets the same `error` and the follow continues. Codex: a worker whose recorded context is an integer over `PLAN_DELEGATE_COMPACT_ABOVE_TOKENS` is first compacted (a `not_measured_since_compaction` size is not) (best-effort, `long-lived-workers.md`); `codex_mesh.py can-follow --session-dir <dir> --to <worker> --role <pass_kind> --claim-pid <pid>` checks followability and takes the roster claim, recording the new role, before any status write (a second concurrent follow exits 2, nothing recorded); `codex_mesh.py follow --session-dir <dir> --to <worker> --role <pass_kind> --message-file <path> --summary-file … --log-file … [--claim-pid <pid>] [--timeout <s>]` then requires that claim (a changed claim exits 1; without `--claim-pid` it refuses and claims on its own pid); `release-follow` releases an unstarted claim and restores the worker's previous role.
- Roster states are typed: `FollowableThread(done|failed|paused)`, `ActiveThread(turn_id, launcher_pid)`, `StartingThread(launcher_pid)`, `WaitingCapacityThread`, `ExhaustedThread`, `EndedThread`, `InvalidThread(reason)`. A stale `ActiveThread`/`StartingThread` whose launcher pid is dead counts as followable. `_follow_refusal` also asks `thread/read` (through `_read_live_turn`) and refuses on a live turn; `_server_availability` returns `LiveServer(port)` or `ServerRestartRequired`. `follow` starts or reuses the app-server, calls `thread/resume`, starts one turn on the same thread and streams it with `_stream_turn(…, follow=True)` (the loop `start` shares), waiting on the started turn id so an earlier `done` cannot end the wait.
- Claude: `agent_bg.sh --attach <mesh_name> <working_dir> <message_file> <summary_file> <log_file> <id_file> [model]` sends through `send.py --to <name> --from launcher --file` (`QUEUED`/`FAILED` is an error), counts the worker's finished assistant turns (`stop_reason` `end_turn` or `stop_sequence`) in `~/.claude/projects/*/<session id>.jsonl` before sending, records `claude-turn-<n>` on the claim, and waits until the count grows and `claude agents --json` reads `idle`. It exits 1 when the worker vanishes.
- Docs: `commands/unit/direct.md` and `docs/delegate/write_prompt_contract.md` say a finished Codex worker is reached only through `implement.sh --to` or `review.sh --to`, later phases, repairs, follow-ups and reviews go to an open worker the same way, and a message to a worker without the launcher is for questions only.

### Worker effort, pane summary, `/unit:report on|off`

- `implement.sh` starts a new Claude worker with `AGENT_BG_EFFORT="${AGENT_EFFORT:-}"` beside `AGENT_BG_LEDGER`; `agent_bg.sh` adds `--effort <level>` to `claude --bg` next to `--model`. An empty registry effort passes an explicit empty value, so no `--effort` is added and a caller's own `AGENT_BG_EFFORT` cannot replace the registry. `--attach` does not change a worker's effort.
- When a worker leaves its summary file empty, `agent_bg.sh` fills it from the pane log in its embedded Python: decode UTF-8 with replacement; strip OSC (`ESC ]` to BEL, `ESC \`, or end of text), CSI (`ESC [ [0-?]* [ -/]* [@-~]`) and two- or three-character escapes (`ESC [ -/]* [0-~]`); strip control characters `\x00-\x08`, `\x0b-\x1f`, `\x7f-\x9f` (newline and tab stay); keep the last 4000 characters. With nothing readable left the summary is `The background agent <name> produced no summary.` `LOG_FILE` is never rewritten and a worker-written summary is never touched.
- `scripts/delegate/unit_notifier.sh <claude_session_id> [on|off]` reads the marker `<session id>` from `PLAN_DELEGATE_ACTIVE_DIR`, else from `/tmp/claude/unit/active` or `/tmp/claude/delegate/active` (it names the session directory; its basename is the run id). No mode creates the `unit-<run id>` instance (`delegate-<run id>` for a run started before the folder rename; old name read until no live marker remains) (`--every` from `PLAN_DELEGATE_PROGRESS_INTERVAL_SECONDS` rounded up to minutes, `--hold`, check `delegate_run.py check`); `off` runs `notifier.sh stop unit-<run id>` and prints `progress updates off: unit-<run id>`; `on` runs `notifier.sh start` and prints `progress updates on: unit-<run id> <next_due line>` (`delegate-<run id>` for a run started before the folder rename; old name read until no live marker remains). A missing or empty marker exits 1 and changes nothing; a `notifier.sh` failure passes its message and status through; a bad mode word or more than two arguments prints the usage and exits 2.
- `/unit:report [tables|on|off]` (`commands/unit/report.md`): `on` or `off` runs `zsh ~/.claude/scripts/delegate/unit_notifier.sh "$CLAUDE_CODE_SESSION_ID" on|off`, relays its line and composes no report; a failure is relayed as printed. A Codex unit has no notifier, so the command says the switch is unavailable there.

## Invariants

- The Stop hook fails open: any error prints one stderr line and exits 0 with no output. It fires only in a session a running production's `showrunner-*` instance targets, and the non-showrunner path stays on the entry point's own imports plus one `conf` read per instance.

- The fn-length hook passes edits with no `Cargo.toml`, unreadable TOML, unknown payloads or internal errors. Unclosed function bodies are skipped; complete earlier functions remain measurable. An internal error prints one `fn-length hook error: <type>: <message>` `systemMessage` and exits 0.

- The hook mirrors clippy exactly: same count, same threshold source, same exemptions, and it fires only where the package's Cargo lints enable `too_many_lines`, so it never blocks code clippy passes. Approved exceptions pass as clippy lets them.

- One checker (`fn_length_lib`) and one hook command string serve Claude and Codex.

- `settings.json` order: the `Edit|MultiEdit|Write` group keeps basedpyright first with the fn-length hook after it; the Stop group keeps `stop-showrunner-footer.py` after the banned-words hook. An edit to either group keeps every entry.

- The footer comes from `showrunner_footer.render_footer` running `dailies_render.py --footer`; the Stop hook and the dailies report share one `footer()`. The reply is read from `last_assistant_message`, never `transcript_path` (at Stop time the transcript lacks the turn's last entry). At most one footer block per stop chain (`stop_hook_active`), so a footer that changes between attempts cannot loop the session. The question check still runs on a retried stop.

- The footer switch is a named state (`FooterState`), never a bare boolean or `None`; a `None` from `Production.schedule` or a missing stamp becomes a named state at the boundary.

- `config/showrunners.json` holds settings only and no script writes it; readers call `load_settings` or `load_settings_from(CONFIG)` on the live checkout's machine-local file. The file stays untracked (`.gitignore` names it).

- Stalled-unit detection belongs to the stall watcher, not `unit_status.sh`. Idleness rests on the pane hash plus transcript and `subagents/` mtimes, never on status-file text.

- The follow-up claim must exist before any status record, so a refusal leaves no stale record. `implement.sh`'s final status write comes after every record step (`finish-pass`, `landed`); unit directors and `launch_implementation.md` read `impl_status_<slot>`. `codex_mesh.py`'s roster states are read by `can-follow`, `follow` and the launcher alike.

- `prepare_session.sh` calls `unit_notifier.sh` with the session id alone to create the instance; that form stays unchanged.

- A failed token acquire exits 1 and a release fails closed when the step group cannot be inspected; callers surface that and never run an unguarded build. Count leftover processes by process group, never `pgrep -f`.

- Times in output carry their zone; the footer judges everything as of its stamp.

## Calibration and gotchas

- **fn-length measurement.** Against clippy on obsidian_knife, 544 of 546 functions match in name and count; the two misses sit inside a `macro_rules!` body. Hana main has 0 non-exempt functions over 100 and 43 exempt ones. Cost: +13.4 ms CPU per Rust edit over a bare launch (budget 20 ms), in-process CPU p95 9.75 ms over 1,544 files, 64.5 ms CPU on a 17,321-line file. Judge cost on CPU time (getrusage children user+sys); wall time under load is noise.

- **fn-length import cost dominates.** `tomllib` loads only when the manifest text names `lints` or a clippy config names the threshold; `dataclasses` and `pathlib` stay off the Rust path (an import test pins this). Classes in `fn_length_lib` are plain `__slots__` classes because frozen dataclasses alone broke the 20 ms budget.

- **fn-length blind spots.** Functions inside `macro_rules!` or `name! { … }` bodies are never measured (clippy sees expanded code the scan cannot expand). Edits made through shell commands (`sed`, heredocs) and growth from rustfmt reflowing a function measured at or under the limit are not seen. A failed `blocks.jsonl` append is silent and never changes the verdict. `cfg(test)` modules in package-root `examples/` targets are skipped because clippy never lints them.

- **Footer cost.** A Stop hook runs at every turn end in every session; the non-showrunner path costs about 4 ms on a quiet machine (bare launch 22 ms quiet, 45–62 ms loaded). Compare cost readings with interleaved bare and hook runs; load swamps any other delta. Replies sent before `<StartUpdates/>` registers the notifier instance are not checked.

- **Footer time.** Adding a `timedelta` to an aware datetime drops `fold`, so the end of a stamped minute is computed in absolute time, or a repeated fall-back hour admits the next hour's readings. Reset count has no history and a stamp has minute resolution, so a reading or Codex reset inside the stamped minute but after the render can still change a re-rendered line; one re-render clears it.

- **basedpyright** exits 3 in every checkout (`pyrightconfig.json` names a `.venv` no checkout has); read its last output line (`0 errors, 0 warnings, 0 notes`), not its exit status. `scripts/hooks` is a pyright execution environment with itself on `extraPaths`, so tests import `fn_length_lib` directly.

- **Stall watch.** `~/.claude/sessions/` keeps stale `<pid>.json` records carrying a live session's id; the live record is the one whose pid answers `os.kill(pid, 0)`. Idle panes stayed byte-identical for 6.5 minutes in a live probe while a busy pane changed only from real activity. A status file reading `implementing` with no live process counts as idle.

- **Notifier launch.** A systemd oneshot (`KillMode=control-group`) kills `&!` children of its `ExecStart`; under `session-notifier` this ended `stall_watch.py` mid-send, so a nudge went out unrecorded and again the next minute. That is why run jobs get their own transient service. `launchctl submit` keeps its job alive (it re-runs every 10 s after exit 0) and launchd ends even `setsid` children when the job exits; a run that must outlive a launchd job needs its own job that removes itself.

- **Launcher races.** A peer turn can overtake a followed turn after `thread/resume`: `follow` exits 1, `impl_status` reads `error`, and the roster stays active while the peer runs, then is restored; a failure of the followed turn survives the peer turn. `board.sh release` exit 3 is benign for `verify.sh`, exit 1 is a real failure. The launcher's own end-of-worker `board.sh release … cargo` ignores failure.

- **Token-wait timing.** `verify.sh` computes `token_wait_s` as the clock after acquisition less the clock before it. The clock is bash's whole-second `SECONDS`, so a real wait under a second can read `1` and any wait can differ from real time by one second either way; `PLAN_DELEGATE_TOKEN_CLOCK_FILE`, when set, replaces it with the integer in that file. `board.sh` waits on a held token with `sleep 3` (the acquire retry loop) and on a contended lock file with `sleep 0.05`. `test_waiting_for_peer_call_records_token_seconds` (`scripts/delegate/test_verify_token_wait.py`) gives each call its own clock file: a stub `sleep` first on `PATH` touches a marker when called as `sleep 3` with `TEST_WAITING` set (the second call's environment only), then blocks on a gate file instead of sleeping, so the marker proves the second call is blocked on the token. The test advances the second call's clock by 20 before releasing the token and asserts waits of exactly 0 and 20. `test_token_wait_uses_elapsed_seconds_when_no_clock_override_is_present` pins the `SECONDS` default with a board stub that sleeps 1.1 s and asserts at least 1. Records are matched to their calls by `-{pid}-` in the record `id`. A change to the `sleep 3` retry interval breaks the marker.

- **Pane summary.** The two-character escape pattern uses the ECMA-48 intermediate and final byte classes, never a dot that matches newlines, or a stray ESC eats the newline or tab after it. An unterminated OSC sequence discards the rest of the pane log, accepted because a worker-written summary never reaches the fallback.

- **Effort.** A Claude worker launched without `--effort` inherits `~/.claude/settings.json` (`modelSettings` → model → `effortLevel`, `xhigh` for Sonnet 5.5), so a pane line reading `thinking with xhigh effort` on a `sonnet:low` worker means the launch dropped the effort, not that the pane misleads.

- **`/unit:report off`.** `unit_notifier.sh` exit 1 covers both no active run and a missing notifier instance; only the message says which, so the command relays it as printed. `off` persists in the notifier instance until `on` or `end_session.sh`. `<ProgressContract/>` in `commands/unit/direct.md` names `/unit:report off` and `/unit:report on` for a Claude unit.

- **Live checks need a person.** An automated bare `claude --bg` probe is refused by the permission classifier, so the worker-effort check (a Claude worker registered `sonnet:low` and launched through `implement.sh` shows `low effort`, not `xhigh`, in its pane) is run by hand.

## Why

- **Block at the edit, not at the lint.** `too_many_lines` fails `verify.sh lint` and costs a repair loop; telling the agent in the same turn is cheaper than the lint round trip. The user wants no long functions, so exceptions stay rare (tests, or a stated reason in real code) and the hook honors clippy's own `allow` and `expect`.

- **Mirror clippy, check the whole file.** In a pedantic-deny crate every non-exempt function over the limit already fails the lint, so reporting all of them says nothing clippy would not; firing only where Cargo lints enable the lint keeps upstream clones such as `~/rust/bevy` quiet. Fail-open on doubt keeps a wrong hook from blocking passing code.

- **A regex tokenizer, not a parser.** The hook runs on every Rust edit beside basedpyright (one matcher group runs in parallel), so import and CPU cost are the budget; a token scan reproduces clippy's count on real code at a few milliseconds.

- **The success threshold is 75% fewer** `too_many_lines` failed steps per 100 hana clippy steps and 75% less sole-cause worker time per day, leaving room for the edits the hook cannot see (shell edits, rustfmt growth).

- **A Stop hook for footers, not a prompt rule.** A rule that lives only in a prompt is one an agent can drop; the hook checks the final lines of every showrunner reply against the same renderer the dailies use, so the footer cannot drift from the report. The reply comes from `last_assistant_message`, and the render takes the reply's own stamp as `--at` so a footer a minute old still matches.

- **The switch is a file keyed by production slug** so it survives compaction, resume and a retargeted notifier instance; the review pause records what it changed so `resume` restores only that, and per-action states make a failed pause retryable.

- **Run jobs get their own service.** A background child stays in the tick's cgroup or launchd job and dies with it; a separate service keeps the run, its watchdog and its final log write alive.

- **Step groups under the token.** A killed verify used to leave its cargo build running while the token moved on, and overlapping builds are what froze the machine; recording the group before the command starts covers the first instant of a step, and release or reclaim stops only an identity-checked group, never one the holder shares with its caller.

- **Follow-up through the launcher.** The launcher is the only process that watches a worker exit, so only it can record the pass, the landed round and the board post; a bare message to a finished Codex worker is refused and leaves no records. One claim per worker, taken before any status write, keeps concurrent follow-ups from corrupting each other's records.

- **`implemented` after the records.** Unit directors read `impl_status_<slot>`; writing it last means a failed ledger write reads `error`, not success.

- **Effort from the registry, plain-text summaries.** A worker that inherits the global effort ignores the registry row that chose its model; pane bytes with terminal codes in a summary corrupt every reader of that file.
