---
description: Hold natedev or the Mac for your work, check quiet, show holds, or release them. Args - `hold <why> [eta HH:MM] [target mac]`, `quiet`, `status`, or `release [target mac]`.
---

`$ARGUMENTS` is `hold <why> [eta HH:MM in the IANA zone you state times in] [target mac]`, `quiet`, `status`, or `release [target mac]`. The default target is natedev.

1. On `hold`, run `python3 ~/.claude/scripts/build_hold/build_hold.py hold --for '<why>'`. The holder is your session, kept by its id, so a rename loses nothing. Pass `--release-eta HH:MM --zone <IANA zone>` only for a measured release time later today. Send the printed notice with `/notify_top_level --here`; showrunners forward it to unit directors. Recipients do nothing: `verify.sh` waits by itself, tests eligible for the Mac keep running there, and an app launch is refused with the holder and reason until release; launch again afterward. Stop only cargo started outside `verify.sh`. `No release after 2 h: ask me` is an escalation, never an ETA. For `target mac`, add `--target mac`; it runs `mac_test.py block` and prints its answer. Do not broadcast the natedev notice for a Mac block. A Mac block's length is set with `/build:mac block <why> hours N`; `--release-eta` and `--zone` are refused for the Mac.
2. Before a held natedev test, run `python3 ~/.claude/scripts/build_hold/build_hold.py quiet`. It waits up to 10 minutes for this user's build processes to end and the 1-minute load to fall below one quarter of the cores. Run it in the background or under Monitor, never in a sleep loop. Exit 1 lists what is busy: let that work end, then retry. CI runners are not asked to stop. For the Mac, wait for the block's free message if its answer says work is still running; see `/build:mac`.
3. `status` runs `python3 ~/.claude/scripts/build_hold/build_hold.py status` and shows its lines. Use `/build:targets` for both targets without changing their records. `python3 ~/.claude/scripts/build_hold/build_hold.py wait` is only for a session about to run cargo outside `verify.sh`. Before release, `registered <id>; wait for direct release before building` means wait for your message; `no hold cycle: wait for the release broadcast` means wait for that broadcast. During release, `release under way; <id> builds now` means build now; `release under way; <id> keeps its queued turn` means wait for your release message. A session whose own call took its open turn is admitted and may launch. `no build hold` means proceed.
4. Release as soon as the work ends, pass or fail: run `python3 ~/.claude/scripts/build_hold/build_hold.py release` in the background with Bash `run_in_background` or under Monitor. A partial release names remaining holders. The last holder releases sessions one at a time, waiting for each memory gate and 60 seconds of settling. Recipients need no `wait`; on the release message, start the build or launch, or run `python3 ~/.claude/scripts/build_hold/build_hold.py nothing-to-build` at once to shorten the turn. A silent session gives up its turn after one minute while another session or build waits; the last one gets 15 minutes. The driver checks an unbound turn every 15 seconds and ends it when its session is gone. Builds and launches arriving after release began start through the memory gate without a turn; a cut session launches without a refusal and gets no second message. A session still queued has its launch refused until its turn opens. After `release stopped:`, do nothing: the new hold's release serves the sessions still waiting. After `release ended:`, do nothing: another release finished it; `still held by` names remaining holders. Use `python3 ~/.claude/scripts/build_hold/build_hold.py release --resume` only if the driver died with no hold in force. On `No hold cycle: broadcast this release to every session.`, send the release with `/notify_top_level --here`. On `Not reached, tell them yourself: <session name> (<reason>)`, tell each named session; the reason is `session gone`, `send failed`, or `queued, no answer`. For `target mac`, add `--target mac`: it runs `unblock` and prints its answer; `--resume` is refused.

## Target state and recovery

- `free`: start your work through its normal gate. `running`: let that job finish; placing a hold prevents new work but does not stop that job.
- `held`: wait for that holder's release, or release your own hold. For a Mac block past its expiry, use `/build:mac unblock`; it stays held until the block file is removed.
- `unreachable`: use `/build:targets --probe`; wait for a working connection before trying Mac work.
- `state unreadable`: use the named path to identify the record. A natedev holder file under `~/.local/state/build-hold/` is repaired by its holder repeating `hold --for '<why>'`; the holder can instead remove its hold with `release`. For `~/.local/state/build-hold-release/current` or its `cycle.json`, `/build:hold release` sets the damaged record aside and ends the hold. A Mac `block.json` or `run.json` under `~/.local/state/mac-test/` needs its damaged file repaired or removed after checking the holder and any job still running; then use `/build:mac block` or `unblock` for the block, or `mac_test.py release --pid <pid>` for a readable kept claim.

## Installed-script refusals

- A set hold-directory variable prints `<script>: <NAME> is set to '<value>'; the installed scripts under <dir> do not run with it. Unset it and run again.` Unset that variable before retrying.
- A changed `HOME` prints the same line naming `HOME`. Run from a shell where `HOME` is the user's home.
- A read-only `HOME` prints `<script>: HOME is read-only in this shell, so the user's home cannot be read. Run again from a shell where HOME is not read-only.` Use a shell where `HOME` is the user's home and is not read-only.
