---
description: Hold natedev or the Mac for your work, check quiet, show holds, or release them. Args - `hold <why> [eta HH:MM] [target mac]`, `quiet`, `status`, or `release [target mac]`.
---

`$ARGUMENTS` is `hold <why> [eta HH:MM in the IANA zone you state times in] [target mac]`, `quiet`, `status`, or `release [target mac]`. The default target is natedev.

1. On `hold`, run `python3 ~/.claude/scripts/build_hold/build_hold.py hold --for '<why>'`. Your session id owns the hold. Add `--keep <pid>` for each run that must continue; repeated holds add to this list, with each PID checked against its start time. The sole holder, kept runs and their children, the user’s own terminal or desktop runs, and shared sccache work may continue. Every other test and build stops at once with the holder and reason, including work already running. Its session gets one release notice; run stopped work again then. `verify.sh` itself continues so eligible tests can go to the Mac; its natedev test children must obey the hold. No run is paused: paused cargo keeps steve slots and cargo locks while wall-clock limits keep running. Pass `--release-eta HH:MM --zone <IANA zone>` only for a measured time later today. Send the printed notice with `/notify_top_level --here`; showrunners forward it. `No release after 2 h: ask me` is an escalation. For `target mac`, add `--target mac`; it runs `mac_test.py block`. Do not send the natedev notice for a Mac block. Mac refuses `--keep`, `--release-eta` and `--zone`.
2. Before a held natedev test, run `python3 ~/.claude/scripts/build_hold/build_hold.py quiet`. It waits up to 10 minutes for remaining builds, including every user's `cargo`, `rustc` and `cargo-nextest` processes to end. Load does not delay it; success prints the 1-minute load and five heaviest processes by current CPU over about one second as the baseline. Run it in the background or under Monitor, never in a sleep loop. Exit 1 lists build counts by user: let those builds end, then retry. CI runners are not asked to stop. For the Mac, wait for the block's free message if its answer says work is still running; see `/build:mac`.
3. `status` runs `python3 ~/.claude/scripts/build_hold/build_hold.py status`. Use `/build:status` for both targets. Before cargo outside `verify.sh`, run `python3 ~/.claude/scripts/build_hold/build_hold.py wait`. It returns at once: 0 permits the build (no hold applies, or you are the sole holder); 10 refuses it and records your session for a release notice when known; 12 means the state cannot be read. Start builds only on 0. After 10, wait for release, then check again.
4. Release as soon as the work ends, pass or fail: run `python3 ~/.claude/scripts/build_hold/build_hold.py release`. With another holder in force, it prints `released; still held by ...`. The release removes its holder file first, then records the end and release fields; notices follow only when no holder file remains. A file that exists is always a hold, even if an old cycle says released. The enforcer exits when no hold remains. Every waiting build can then enter its memory gate, which orders the builds. Each recipient gets one notice to start builds; no answer is needed. On `No hold cycle: broadcast this release to every session.`, send the release with `/notify_top_level --here`. On `Not reached, tell them yourself: <session name> (<reason>)`, tell each named session; reasons are `session gone`, `send failed`, or `queued, delivery unconfirmed`. `release --resume` refuses while any holder file exists; use a normal release for that file. For `target mac`, add `--target mac`: it runs `unblock` and prints its answer; `--resume` is refused.

## Build calls during a natedev hold

The Bash PreToolUse hook `scripts/hooks/pre-tool-use-build-hold-guard.sh` starts no Python when the hold directory has no entry or the input has neither `cargo` nor `verify.sh`. Otherwise it passes the input to `pre-tool-use-build-hold-guard.py`. The guard refuses building `cargo` calls and `verify.sh check`, `lint`, `build`, `doc` and `clippy` for a non-holder while any other session’s holder file exists. It uses `scripts/build_hold/hold_applies.py`, which shares `wait-local`'s hold and caller check. The refusal names only holders in force: `natedev builds are held by <holder>. Keep working, writes included. Run tests with verify.sh test: they go to the Mac. Run check, lint and builds after the hold ends.`

The sole holder may build. `verify.sh test` and non-building calls pass. The helper exits 0 with the refusal on stdout, 1 with no output when builds may run, or 2 with the read error on stderr; the hook allows the call on a read error.

## Target state and recovery

- `free`: start your work through its normal gate. `running`: let that job finish; a natedev hold stops tests and builds outside its allow rules, including work already running; a Mac block lets its running job finish.
- `held`: wait for that holder's release, or release your own hold. For a Mac block past its expiry, use `/build:mac unblock`; it stays held until the block file is removed.
- `unreachable`: use `/build:status --probe`; wait for a working connection before trying Mac work.
- `state unreadable`: use the named path to identify the record. A natedev holder file under `~/.local/state/build-hold/` is repaired by its holder repeating `hold --for '<why>'`; the holder can instead remove its hold with `release`. For `~/.local/state/build-hold-release/current` or its `cycle.json`, `/build:hold release` sets the damaged record aside and ends the hold. A Mac `block.json` or `run.json` under `~/.local/state/mac-test/` needs its damaged file repaired or removed after checking the holder and any job still running; then use `/build:mac block` or `unblock` for the block, or `mac_test.py release --pid <pid>` for a readable kept claim.

## Installed-script refusals

- A set hold-directory variable prints `<script>: <NAME> is set to '<value>'; the installed scripts under <dir> do not run with it. Unset it and run again.` Unset that variable before retrying.
- A changed `HOME` prints the same line naming `HOME`. Run from a shell where `HOME` is the user's home.
- A read-only `HOME` prints `<script>: HOME is read-only in this shell, so the user's home cannot be read. Run again from a shell where HOME is not read-only.` Use a shell where `HOME` is the user's home and is not read-only.
