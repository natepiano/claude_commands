# Worktree Fit

**Purpose:** Given a design plan, work out *where it should live* — which repo, which branch, branched from what — so the work integrates with everything else in flight with the least pain later. Surveys every worktree across the project's repos, compares what each in-flight branch is touching against what the plan will touch, and returns a placement recommendation with a merge and sequencing plan.

This answers four questions, in this order:

1. **Base point** — branch from `main`, or from an in-flight feature branch?
2. **Interim merges** — are any needed before this work lands, and in which direction?
3. **Sequencing** — when several plans are in flight, what order minimizes rework?
4. **Integration risk** — which specific files will collide, and with whom?

It does **not** create anything. It ends by handing an approved recommendation to `/make_a_worktree`.

**Usage:** `/worktree_fit [design doc path or topic] [into <worktree-name>]`

**Arguments:**
- A design doc path, or a topic to infer from the conversation. If empty, infer the plan from the current conversation.
- An optional `into <worktree-name>` clause when the user already has a destination in mind. That changes the job from *recommend a placement* to *evaluate this placement and say whether it holds*.

<ProjectTopology>
**What this project actually is.** `~/rust/bevy_hana` and `~/rust/hana` are two git repos but one extended project; they are expected to become a single workspace eventually. Placement advice must work today *and* survive that merge — do not propose structures that depend on the split being permanent, and do not preempt the merge either.

**Convention.** The primary checkout (the directory that owns `.git`) stays on `main`. Every branch lives in its own worktree, created as a sibling directory under `~/rust/`. So `git worktree list` in the primary repo is the authoritative map of what is in flight.

**Two kinds of worktree, and they are not interchangeable:**

- **Feature worktree** — hand-created via `/make_a_worktree`, named for its work (`hana_tool_graph`, `bevy_clerestory_reconnect`, `hana_diegetic_widgets`), on a long-lived branch. These are legitimate base points and legitimate merge partners.
- **style_fix worktree** — machine-generated by clean-fix (`~/.claude/scripts/clean-fix/`), named `<project>_style_fix`, carrying a `.clean-fix-project` marker file. Created and destroyed by the every-10-minute job; see `/clean_fix`. These are **ephemeral and never a base point** — see <HardRules/>. They matter to this analysis only as a *collision source*: style fixes rewrite code mechanically across a project, so a plan landing in the same files should expect churn.

**Cross-repo dependency direction is one-way and hard.** `~/rust/hana` consumes `bevy_hana` crates as **published crates.io versions** (`bevy_clerestory`, `bevy_kana`, `bevy_lagrange`, …) and **git-rev pins** (`hana_prosody`) — not path dependencies. Consequences the analysis must state whenever a plan spans both repos:

- The `bevy_hana` side lands **first**. The `hana` side cannot consume it until it is published or a rev is pinned.
- During development the bridge is a temporary `[patch]` section in `hana/Cargo.toml` pointing at the local `bevy_hana` worktree. Say so explicitly, and say it must be removed before the hana side merges.
- A plan that adds a *new* `bevy_hana` crate therefore has a mandatory two-phase shape. Never present it as one undifferentiated piece of work.

Repos default to `~/rust/bevy_hana` and `~/rust/hana`. Other repos (`~/rust/nateroids`, `~/rust/bevy_brp`, …) join the scope only when the plan names them as consumers or when the user asks.
</ProjectTopology>

---

<HardRules>
These are not preferences. Violating one produces advice that cannot be executed.

- **Never recommend branching from a `*_style_fix` worktree.** It is deleted on the next clean-fix run and its history is not a stable base. Its changes reach `main` through its own merge path.
- **Never recommend creating a branch in the primary checkout.** The primary stays on `main`; branches live in worktrees.
- **Never recommend `git stash`.** Expressly prohibited by the user. When a worktree has uncommitted work standing in the way, the answer is a commit (a WIP commit is fine) or a different worktree.
- **This command creates nothing.** No `git worktree add`, no branch, no merge, no checkout. It surveys, recommends, and hands off. Survey agents are read-only.
- **Branch-switching and worktree operations need `dangerouslyDisableSandbox: true`** (`checkout`, `merge`, `rebase`, `worktree remove`), as does any `gh` command. Read-only git (`log`, `status`, `rev-list`, `worktree list`, `diff --stat`) runs fine sandboxed. Note this in the handoff for any command that follows.
- **A recommendation with no named collisions is incomplete.** "Branch from main" is only useful alongside *what it will conflict with and when*. If the survey found genuinely zero overlap, say that explicitly — it is a finding, not an omission.
</HardRules>

<ResolveScope>

1. **Find the plan.** From `$ARGUMENTS`, or the doc the user has been working in this session, or the conversation topic. If more than one candidate plan exists, ask which one — do not merge them.
2. **Detect an `into <worktree>` clause.** If present, set `${TARGET_WORKTREE}` and treat the job as *evaluate this placement*. Otherwise leave it unset and recommend one.

4. **Confirm in one line, then proceed without waiting:**
   > `Fitting <plan> across <repo>, <repo>. Surveying worktrees…`

Create todos for: survey, fit analysis, recommendation, handoff.
</ResolveScope>

<SurveyInParallel>
**Goal:** Gather the two halves of the picture — what is in flight, and what the plan will touch — without spending main-session context on either.

Launch these agents **in a single message** so they run concurrently. Use `subagent_type: general-purpose`. Every prompt must state: **read-only — run no command that writes, switches branches, creates worktrees, or commits.**

**One agent per repo in scope.** Prompt each with the repo's absolute path and this checklist:

```
Read-only git survey of <repo path>. Run no command that writes, switches
branches, creates a worktree, or commits.

For the repo itself:
  git -C <repo> worktree list
  git -C <repo> branch -vv --all

For EVERY worktree, including the primary:
  - path, branch, whether it is the primary checkout (owns .git)
  - classification: primary / feature worktree / style_fix worktree
    (style_fix = name ends in _style_fix, or a .clean-fix-project file exists
    at its root)
  - divergence from main:
      git -C <worktree> rev-list --left-right --count main...<branch>
    report as "<N> behind, <M> ahead"
  - the fork point and its date:
      git -C <repo> log --oneline -1 $(git -C <repo> merge-base main <branch>)
  - uncommitted state: git -C <worktree> status --porcelain (report the count
    and whether anything is staged; do not dump the file list unless small)
  - whether the branch is pushed and how it sits vs its upstream
  - LAST COMMIT DATE — a branch untouched for weeks is a different risk than
    one committed to this morning. Report it.

For every non-primary branch, the TOUCH SURFACE — this is the most important
part of your report:
  git -C <repo> diff --stat main...<branch>
  Summarize as the set of top-level areas it modifies (crate names, and
  directories one or two levels below crates/), with the heaviest-churn paths
  named specifically. Not a full file list — the shape of what it is rewriting.

Also report, in one sentence each, what each in-flight branch is FOR — read its
commit subjects (git log --oneline main..<branch> | head -20) and say what the
work is, in plain language.

Return a compact structured report. No recommendations — just state.
```

**One agent for the plan's touch surface.** Give it the plan doc's absolute path and the repo paths:

```
Read <plan doc>. Determine what this work will TOUCH when implemented — do not
evaluate or critique the plan.

Report:
  - which repos it modifies, and for each: which crates, which directories,
    which specific existing files it edits or moves
  - what it CREATES that does not exist yet (new crates, new modules) — these
    are collision-free by construction, and separating them from edits to
    existing files is the single most useful thing in your report
  - whether it spans both repos, and if so which side must land first
  - whether it changes any dependency declaration, workspace member list, or
    published-crate version
  - roughly how large the change is: a handful of files, or a broad sweep

Where the plan names a file, verify it exists at that path and say so. Where the
plan is vague about location, say it is vague rather than guessing.

Read-only. Run no command that writes.
```

Yield after launching. Task notifications signal completion — do not poll.

If an agent returns nothing usable, say so and either relaunch that one or proceed on partial data with the gap stated. Never treat a failed survey as an empty one.
</SurveyInParallel>

<AnalyzeFit>
**Goal:** Turn the survey into a placement. This is main-session work — it is the judgment the fan-out was buying context for.

**1. Build the overlap matrix.** For each in-flight branch, intersect its touch surface with the plan's. Classify:

- **Disjoint** — no shared paths. The branches can proceed in parallel and merge in any order.
- **Adjacent** — same crate, different modules. Mergeable, but expect import/module-tree conflicts at the `mod.rs` level and say which files.
- **Overlapping** — the same files. This is where sequencing is forced.
- **Superseding** — the in-flight branch is rewriting the very code the plan is built on. The plan's assumptions may already be stale; flag this loudly, because it is a plan-correctness problem, not just a merge problem.

**2. Choose the base point.** In preference order:

- **`main`** — correct whenever the plan is disjoint or adjacent. Simplest history, no dependency on someone else's unlanded work. Prefer it; a plan that mostly *creates* new crates or modules almost always belongs here.
- **An in-flight feature branch** — correct only when the plan genuinely *builds on* unlanded work: it needs types, APIs, or files that exist only on that branch. State what specifically it needs. This inherits that branch's fate — if it is abandoned or heavily rewritten, this work goes with it. Say that cost out loud.
- **`main` plus a stated merge-in** — the middle path, and often the right one: branch from `main`, and merge the in-flight branch in *once it lands*, at a named point. Use this when the plan needs the other work eventually but not to start.

Never propose a style_fix worktree as a base (<HardRules/>).

**3. Decide interim merges, with direction and trigger.** Each recommended merge must name all three:

- **Direction** — `main` → feature keeps a long-running branch from drifting and is nearly always safe. Feature → feature couples two fates and needs a reason. Feature → `main` early is only correct when the shared foundation genuinely is done.
- **Trigger** — the event that makes the merge due ("once `feature/widgets` lands", "before starting phase 3", "when the new crate is published"), not a date.
- **Cost** — what breaks if it is skipped, in concrete terms.

For long-lived branches far behind `main` (say, 20+ commits), a `main` → branch merge before layering new work on top is usually right, and cheaper the sooner it happens. Say which branches are in that state.

**4. Sequence, when more than a couple of things are in flight.** Produce an explicit order. Drive it by:
- **Forced edges first** — cross-repo publish/pin ordering (<ProjectTopology/>), and any plan that consumes another's output.
- **Then overlap** — the branch touching the most contested files should land first; everything else rebases onto it once rather than fighting it repeatedly.
- **Then staleness** — the branch that has been open longest, or is furthest behind, is the one accruing merge debt.

State the sequence as a numbered list of *landings*, each with what unblocks it. If two items are genuinely independent, say so rather than inventing an order.

**5. If `${TARGET_WORKTREE}` was set**, answer that question directly: does the plan fit there? If not, name the specific conflict and give the alternative. Do not quietly substitute a different recommendation for the one that was asked about.
</AnalyzeFit>

<PresentRecommendation>
**Goal:** A diagram, then an approvable step list. **Not an essay.** The user is deciding where work goes and in what order — they should be able to see that in one screen and approve it without reading paragraphs.

**Never present this through AskUserQuestion or any survey/questionnaire UI.** Ordinary message text; the user answers by typing.

Output exactly four things, in this order, and nothing else.

---

**1. The headline — one sentence, before anything else.** It states the location, the base, and the reason, in that order:

> `<worktree path> off <repo>/<base branch> — <the single reason, one clause>.`

The reason is the *one* fact that decided it, not a summary of the analysis. "nothing in flight touches `bevy_kana`" is a reason; "it fits best with the current work" is not. If the plan spans repos and only one side is being placed now, the sentence says so:

> `~/rust/bevy_hana_rubric off bevy_hana/main — nothing in flight touches bevy_kana, and hana_rubric is a new directory. The hana side waits for init/hana_catalyst.`

Never open with preamble, a restatement of the request, or a heading. This sentence is the first thing on screen.

**2. The topology diagram.** ASCII — this renders in a terminal, so no mermaid. One line per branch: repo, main tip, each worktree with ahead/behind, and where the new work attaches. Mark each branch's relationship to the plan with a symbol. Under ~20 lines. Shape:

```text
bevy_hana   main df97b2b2 ──┬── feature/reconnect    33↑  0↓   ○  bevy_clerestory
                            ├── feature/widgets      40↑ 10↓   ○  hana_diegetic
                            └── feature/rubric  ★ NEW          ●  hana_rubric + bevy_kana

hana        main 2625faa  ──┬── init/hana_catalyst   67↑  1↓   ◆  input/global_shortcuts.rs
                            │                                     +283 −4
                            └── (hana side) ✗ not yet ── blocked by catalyst landing

  ● this work    ○ disjoint, ignore    ◆ collides    ✗ deferred
```

**3. The step list.** Numbered, grouped into stages. Each stage carries a one-line header saying what it accomplishes and what gates it. Each step is **one line of concrete action** — a real command where there is one — followed by **one indented line of rationale**. No step without a why; no why longer than a line.

```text
## Stage 1 — <what this stage achieves>   (gated by: nothing / <event>)

  1. <concrete action, ideally the literal command>
     └ <why, one line>
  2. <…>
     └ <…>

## Stage 2 — <…>   (gated by: stage 1 + <external event>)

  3. <…>
     └ <…>
```

Rules for the steps:
- A step is something a person does in one sitting. "Implement the crate" is not a step; "create the worktree", "publish bevy_kana 0.2.0", "reconcile PermanentShortcutsContext against D8" are.
- Where a step is blocked on something outside this session (a branch landing, a publish), say so in its stage header rather than burying it.
- Collisions and corrections are steps too, not commentary — "reconcile X against Y" is a step someone has to do.
- If a stage cannot start yet, mark it and do not renumber later.

**4. The approval line.** Offer both granularities:

> `approve all / approve stage 1 (recommended — <one-line reason>) / step N only / revise / elaborate`

On `elaborate`, expand exactly one step or one stage — not the whole plan — and re-present the same line.

---

**What does NOT go in this output:** the reasoning that produced the placement. Findings, overlap analysis, dependency hazards, and doc corrections belong in the `## worktree placement` section written to the plan doc (see <HandOff/>), where they are durable and re-readable. The presentation carries the diagram, the steps, and one line of why per step. If the user wants the analysis, `elaborate` gives it to them a piece at a time.
</PresentRecommendation>

<HandOff>
**Goal:** Turn an approved recommendation into the next command, and preserve the parts that would otherwise be lost.

**Approval is per stage or per step, whatever the user gave.** Execute only what they approved, then stop and re-present the remaining stages. Never run a step from a stage they did not approve, and never treat "approve stage 1" as licence to start stage 2.

**On any approval:**

1. **Write the analysis to the plan doc first**, before executing anything. This is the durable artifact; the terminal output is not. Months later, "why is this branched off `feature/widgets`?" needs an answer that outlives the session — and `/plan:to_phased_plan` reads this section to phase the work correctly.

   **The section is a contract with `/plan:to_phased_plan`.** Use this exact heading and these exact field labels — that command finds them by name, so a renamed heading or a reworded label silently disables the integration:

   ```markdown
   ## Worktree Placement

   **Base:** `<worktree path>` — `<repo>/<branch>` off `<base branch>` @ `<sha>`
   **Status:** created | not yet created

   **Gates:**
   - `G1` — <what is blocked> — blocked by <the unblocking event> — <one-line why>
   - `G2` — …

   **Scope now:** <which repo / crates can be worked immediately>
   **Scope deferred:** <what waits, and behind which gate id>

   <Everything else — collisions, dependency hazards, corrections, the full
   reasoning — as ordinary prose below. Only the labelled fields above are read
   mechanically.>
   ```

   A gate is anything that makes work unrunnable until an event outside the plan occurs: another branch landing, a crate publish, a decision the user owes. Give each a stable `G<n>` id — the phased plan cites them. If there are no gates, write `**Gates:** none` rather than omitting the field, so the absence is deliberate rather than an oversight.

   **This section does not decide where the phased plan is written.** `/plan:to_phased_plan` rewrites its source doc in place unless given `--out <path>`, and that flag is the user's call at invocation time — a worktree may exist to initialize a crate or to carry one big feature, and neither shape implies where its plan belongs. If the placement suggests the plan should live with the code, say so in the prose as a recommendation and name the path; do not encode it as a field.
2. **Execute the approved steps in order**, reporting each as it completes in one line. Stop at the first failure and say what broke.
3. **Mark steps that are not yours to run** — a publish, another branch landing, a decision the user owes. Do not silently skip them; name them as the reason the next stage is still gated.

**The `/make_a_worktree` trap.** That command runs `git rev-parse --show-toplevel` and `git worktree add ../<name>` against **the current working directory's repo**. When this session's cwd is not the repo the worktree belongs in — which is common, since plan docs often live in a separate docs repo — invoking it silently creates a worktree of the wrong repository. Check first:

- cwd's repo **is** the target repo → invoke `/make_a_worktree <name>`; it handles branch creation, `settings.local.json`, and the clean-fix redirect offer.
- cwd's repo is **not** the target → do it explicitly and say why you are bypassing the command:
  ```bash
  git -C <target-repo> worktree add ../<name> -b <branch> [<base-branch>]
  ```
  then copy `<target-repo>/.claude/settings.local.json` into the new worktree if it exists, and run the clean-fix detect step from `/make_a_worktree`'s `<OfferCleanFixRedirect/>` yourself.

Both paths need `dangerouslyDisableSandbox: true` (<HardRules/>).

**Base other than `main`:** `git worktree add ../<name> -b <branch>` branches from the current HEAD of the primary checkout. A non-`main` base needs the base branch as a trailing argument. Say so explicitly rather than letting the wrong base pass through silently.

**Spans both repos:** restate the two-phase shape once — which repo's worktree exists now, what has to land and be published or pinned, and that any temporary `[patch]` must come out before the second side merges.

**On `different base`:** re-run <AnalyzeFit/> step 2 against the user's choice, state the consequences you see, and re-present. The user's call stands — say the cost once, then proceed.

**On `defer`:** record the recommendation and its trigger in the plan doc anyway, so the next session picks up the analysis rather than repeating this command. Say which branch landing unblocks it.
</HandOff>
